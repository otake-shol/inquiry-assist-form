# 問い合わせ対応の枠組み

この文書は、ほかの仕様（`api-contract.md`、`ux-principles.md`、`skill-architecture.md`）より上位に置く。機能を足すか迷ったら、ここに戻って判断する。

図は https://claude.ai/artifact/Y3H5kCLTdc6N3cSArnaaDr にある（置き場所の格子、進み方の路線、業務フロー）。

## 1. 定義

> 問い合わせとは、目的に向かう途中で止まった人が、自分では埋められない不足を埋められる相手に状況を渡し、動いてもらおうとする働きかけ。

| 要素 | 意味 | 欠けると |
| --- | --- | --- |
| 目的 | 本人は何かをしようとしている | 感想や雑談になる |
| 不足 | 知識、決定、実行のどれかが足りず、進めない | 単なる調べものになる |
| 相手 | 埋められる相手が、本人とは別にいる。相手は人とは限らず、AI も含める | 自分で調べて終わる |
| 状況の受け渡し | 渡るのは問いではなく、問いになる前の状況 | — |

不足は3種類ある。

| 不足 | 埋まるとは | 埋める役割 |
| --- | --- | --- |
| 知識 | 本人が分かる | AI（資料に根拠がある場合）。なければ担当者 |
| 決定 | 決まる | 担当者（既にある仕様や先例を当てはめる場合）。新しい決定は仕様の持ち主 |
| 実行 | 行われる | 担当者 |

## 2. 構造と、解く課題

知っていることが、2人の間で食い違っている。本人は状況を知っているが、埋め方を知らない。相手は埋め方を知っているが、状況を知らない。問い合わせ対応の仕事は、この2つの「知らない」を突き合わせること。

ここから、解く課題が4つ出てくる。

| 課題 | 生まれる理由 | 手段 |
| --- | --- | --- |
| 伝える費用 | 状況を知る人と、埋め方を知る人が別。相手に通じる形に直す作業が要る | 受付（AI が聞き、言い直す） |
| 待つ費用 | 埋められる人の時間は限られる。その間、本人は止まったまま | AI が「分かる」を運ぶ。誰の番かを状態にする |
| 届け先を誤る費用 | 不足の種類と、それを埋められる人の対応が見えない | 置き場所（格子）と、3つの区間 |
| 繰り返す費用 | 埋めた結果が残らず、同じ不足が何度も現れる | 記録、先例、マスごとの集計 |

**4つの課題のどれにも効かない機能は、作らない。**

## 3. 方針

- **型は Jira Service Management に揃える。** リクエストタイプ、ステータス、解決状況、キュー、期限などの実証済みの型を借り、概念を発明しない。
- **独自にするのは、内製の理由に効く部分だけ。** 社内の資料を外に出さずに AI に読ませること。関係者の要望にすぐ応えられること。
- **設定として持つ。** システム、機能、種類、担当、進み方、期限をコードに書き込まず、設定で変えられるようにする。この文書が定義する枠組みは、そのまま設定できる項目の一覧になる。
- **AI は門番ではなく伴走者。** 問い合わせの件数は目標にしない。

## 4. 全体像

5つの面と、2つの土台でできている。

| 面 | 中身 | Jira Service Management で相当するもの |
| --- | --- | --- |
| 1. 入口 | 本人が、選択肢を押して1問ずつ答える。文章で書くこともできる | ポータル、メール、チャット |
| 2. 受付 | 足りないことを聞く。押して答えた内容から問いを組み立て、本人に確かめる | リクエストタイプの選択とフォーム |
| 3. 対応 | 3つの区間を、誰かの番として進む | ワークフロー、キュー、承認 |
| 4. 終了 | 終わり方を決めて閉じる | 解決状況、自動クローズ |
| 5. 蓄積と改善 | 先例、マスごとの集計、資料を育てる | ナレッジベース、レポート |
| 土台: 設定 | システム、機能、種類、担当、期限 | プロジェクトの設定 |
| 土台: 計測 | 期限を守れたか、用は足りたか | SLA、満足度の調査 |

入口は、選択肢を押していく一問一答を基本にする。聞く順は、種類（何をしたいか）、システム、機能、マスごとの詳しい質問。書くより押すほうが、始める負担が軽いため。どの質問でも「わからない」を選べ、どの時点でも文章で書く道に切り替えられる。

種類を本人が選ぶ点は、JSM と同じ。違いは受付にある。項目を埋めて送るのではなく、押して答えた内容から AI が問いの文章を組み立て、「つまり、こういうことですね」と本人に確かめる。定義の「渡るのは問いではなく、問いになる前の状況」は変わらない。問いを作る仕事は、引き続きこちらが引き受ける。

Jira Service Management との対応は、公式のドキュメントで確かめた。事実の記録は `jsm-benchmark.md`、採否の判断は `requirements.md` の6章にある。

## 5. 登場人物

役割であり、1人が複数を兼ねてよい。

| 役割 | 責任 | できないこと |
| --- | --- | --- |
| 本人 | 状況を渡す。不足が埋まったかを伝える | 他人の問い合わせを見る。対応の進み具合を変える |
| AI | 伝える費用と待つ費用を下げる。担当者には材料、判断の案、下書きを出す | 閉じる、決める、作業する。根拠を確かめられない内容を本人に見せる |
| 担当者 | 自分の番の件を、終わりまで運ぶ | 新しい仕様を1人で決める |
| 仕様の持ち主 | 相談を受け、新しい決定を下す。決定は先例として残る | — |
| 設定する人 | 枠組みを保つ（システム、機能、種類、担当、期限の設定） | — |

**目指す状態は、担当者が AI を使い切って、自分のところで完結させること。** 仕様の持ち主は進み方の途中に立つ人ではなく、相談・エスカレ先として存在する。

問い合わせがどこで終わるかを、段と呼ぶ。

| 段 | 誰で終わるか | ここで終わる問い合わせ |
| --- | --- | --- |
| 0段 | AI と本人 | 知識の不足で、資料に根拠があるもの |
| 1段（目標） | 担当者 | 実行の不足。決定の不足のうち、既にある仕様や先例を当てはめれば済むもの |
| 2段 | 仕様の持ち主 | 新しい決定が要るもの |

担当者が自分で決めてよいのは、既にある仕様や先例を当てはめる判断まで。新しい決定が要るものだけ、仕様の持ち主に相談する。迷ったら相談する。

2段に上がった件は、必ず先例を1つ残す。先例が増えるほど、AI が担当者に出せる案が増え、1段で終わる件が増える。

担当者に対して AI が出すものは4つ。

1. 判断の材料（問い、いまの動き、根拠、似た先例）
2. 判断の案（相談が要るかどうかも示す）
3. 作業の手順の案（対象、操作やコマンド、順序、結果の確かめ方、元に戻す方法）
4. 本人への返信の下書き

担当者はこれを確かめて決め、送る。AI は作業を実行しないが、手順はできるだけ具体的に示す。本人に対しても同じで、使い方の問いには操作の順を示し、頼まれた作業でも本人が自分でできる手順があればそれを示す。

## 6. 扱うもの

枠組みが持つものは4つ。

| もの | 持つ項目 |
| --- | --- |
| 問い合わせ | 置き場所（システム、機能、種類）と緊急度。本人が書いた状況、言い直した問い、やり取り、調べて分かった事実と根拠。区間、誰の番か、終わり方。本人、担当者 |
| マス | システム、機能、種類。担当者、相談先、調べる資料の範囲、毎回聞くこと、期限の目安。そのマスの問い合わせと先例が溜まる |
| 変更の記録 | いつ、どのシステムのどの機能で、何が変わったか。予定か、行われたか。AI が調査の材料にし、入口のお知らせに出し、関係する問い合わせの本人に知らせる |
| 先例 | どのマスの、どんな状況についての決定か。決定の内容（意図どおり、不具合、受ける、受けない、採用する、見送る）。理由、決めた人、元になった問い合わせ、日付。後の決定で上書きされていないか |

**AI が返した答えは、知識として溜めない。** 知識の出どころは資料（コード、FAQ）であり、答えは毎回、資料から調べ直す。溜めた答えは、資料が変わると古くなる。先例は人が下した決定で、ここにしか残らないため、溜める。

問い合わせの多いマスについては、AI が FAQ の下書きを出し、人が確かめて資料に加える。答えを溜める代わりに、資料そのものを良くする。

問い合わせの記録の中身は、出どころごとに欄を分けて持つ。本人が選んだこと・書いたこと、照合できた資料の記述、照合できなかった内容、先例、AI の案の5つ。どの欄に入るかは、AI ではなくコードが決める。AI の案には、基づく事実と先例を添え、基づくものがない案は出さない。担当者が AI の出したものを素早く確かめるには、出どころが見えている必要がある。

### 置き場所

種類 × 機能 の格子を、対象システムの数だけ重ねる。1件の問い合わせは、どれか1枚の、どれか1マスに置かれる。

格子の軸（システムと機能）は、そのままシステムと機能の台帳になる。システムと機能ごとに、担当、相談先、資料の場所、関連するシステムを持つ。マスの担当は、当番表（期間ごとの担当者）として持てる。

- **種類の行**は全システムで共通。使い方を知りたい、仕組みを知りたい、おかしいかもしれない、やってほしい、変えてほしいの5つ。行は設定で足せる。
- **機能の列**はシステムごとに違う。問い合わせる人が自分で選べる粒度（画面やメニューの名前）にする。「わからない」の列を必ず持つ。
- **障害は種類ではない。** 緊急度として、どの行にも重ねる。
- 種類、システム、機能は本人が選ぶ。本人が「わからない」と答えた軸、または文章で書いた場合だけ、AI が置く。担当者が直せる。
- 1マスに収まらない場合は、主のマスを1つ決め、ほかを副として持つ。種類が変わったら置き場所を移し、履歴を残す。

## 7. 状態と遷移

### 区間

進み方は、不足の3種類に対応する3つの区間でできている。種類ごとに、通る区間が違う。

| 種類 | 通る区間 |
| --- | --- |
| 使い方を知りたい | 分かる |
| 仕組みを知りたい | 分かる（資料になければ、決まるへ移る） |
| おかしいかもしれない | 分かる → 決まる → 行われる（意図どおりなら、決まるで終わる） |
| やってほしい | 分かる → 決まる → 行われる（本人が自分でできる手順が資料にあれば、分かるで終わる） |
| 変えてほしい | 決まる（実際に変える作業は、問い合わせ対応の外） |

### 状態

1件の状態は「どの区間にいるか」と「誰の番か」の組で表す。終わった件は終わり方を持つ。

| 区間 | 誰の番になりうるか |
| --- | --- |
| 分かる | AI、本人、担当者（AI が答えられなかった場合） |
| 決まる | 担当者、仕様の持ち主（相談中）、本人（聞き返されたとき） |
| 行われる | 担当者、本人（聞き返されたとき） |

区間（何の不足か）と段（誰で終わるか）は別の軸。AI が答えられなくても不足は知識のままなので、区間は「分かる」のまま、番だけが担当者に移る。

### 終わり方

「不足は埋まったか」の1つの問いで分ける。

| 終わり方 | 不足は埋まったか | 誰の一言で終わるか |
| --- | --- | --- |
| 解決済み | 埋まった | 本人が解決を伝えた。答えたのが AI でも担当者でも同じ |
| 回答済み | 分からない | 誰も言っていない。結果を伝えた後、返事がないまま期間が過ぎた。本人はいつでも開き直せる |
| 見送り | 埋めないと決めた | 担当者が、応じないと決めて伝えた（受けない、見送る、直さない） |
| 取り下げ | 本人がやめた | 本人が取り下げた。答えを返す前に本人が離れた件を含む（入力の途中で止まった、担当者の聞き返しに返事がないまま期間が過ぎた）。時間で取り下げになった件は、本人が開き直せる |

- **AI は問い合わせを閉じない。** 閉じるのは、不足を持っていた本人。担当者が閉じるのは、応じないと決めた場合だけ。
- 答えたのが AI でも担当者でも、結果は本人が確かめる。手順を伝えただけ、作業を終えただけでは閉じない。
- 確かめる言葉は、答えが分かったかではなく、目的が進むかを尋ねる。問い合わせは、目的に向かう途中で止まった人の働きかけだから。本人が尋ねたことと、本当に必要なことが違う場合に、本人が「いいえ」と答えやすくなる。
- 本当に必要なことを、仕組みで完全に見抜くことはできない。目的を尋ねる質問は一律には足さず、言い直しの文に読み取れた目的を含めることと、上の確かめ方で、ずれに気づく機会を作る。漏れた件は、本人の「いいえ」で担当者に届く。
- 担当者が何をしたか（答えた、判断した、作業した）は、終わり方ではなく記録の中身として持つ。

### 遷移

| 起こす人 | 出来事 | その後 |
| --- | --- | --- |
| 本人 | 選択肢を押して答える、または文章で書く | 問い合わせができる。AI の番 |
| 本人 | 質問に答える、言い直しを確かめる | AI の番 |
| 本人 | 「解決した」と伝える | 終わり（解決済み） |
| 本人 | 「解決していない」と伝える | 担当者の番 |
| 本人 | 答えを待たずに担当者へ送る（問いを確かめた後に限る） | 担当者の番。AI の調査は裏で続き、材料と案が担当者に渡る |
| 本人 | 聞き返しに答える | 聞き返した人の番 |
| 本人 | 取り下げる | 終わり（取り下げ） |
| 本人 | 終わった件に追記する | 担当者の番で開き直す |
| AI | 質問する、言い直す | 本人の番 |
| AI | 答える（知りたい系で、根拠がある） | 本人の番。結果を確かめる |
| AI | 自分でできる手順を示す（やってほしいで、資料に手順がある） | 本人の番。自分で行うか、担当者に頼むかを選ぶ |
| AI | 材料と案を揃える（おかしいかもしれない、やってほしい、変えてほしい） | 担当者の番 |
| AI | 答えられない | 担当者の番 |
| 担当者 | 本人に聞き返す | 本人の番 |
| 担当者 | 仕様の持ち主に相談する | 持ち主の番 |
| 担当者 | 判断して、結果を伝える | 本人の番。結果を確かめる |
| 担当者 | 判断して、作業に進む | 行われるの区間へ。担当者の番 |
| 担当者 | 作業を終えて、結果を伝える | 本人の番。結果を確かめる |
| 担当者 | 応じないと決めて伝える | 終わり（見送り） |
| 担当者 | マスを置き直す | 種類が変われば、区間も変わる |
| 仕様の持ち主 | 決める | 先例が1つできる。担当者の番 |
| 時間 | 期限が近づく、過ぎる | 担当者に知らせる |
| 時間 | 返事がないまま、知らせる期間が過ぎる | 本人に知らせる |
| 時間 | 結果を伝えた後、返事がないまま、終える期間が過ぎる | 終わり（回答済み） |
| 時間 | 聞き返した後、返事がないまま、終える期間が過ぎる | 終わり（取り下げ） |
| 時間 | 入力の途中のまま期間が過ぎる | 終わり（取り下げ） |
| 時間 | 終わってから開き直せる期間が過ぎる | 以後の追記は新しい件になる |

- 終わった件への追記は、AI の番には戻さない。前の答えで足りなかった合図であり、同じ AI に戻すと同じ答えを繰り返すおそれがあるため。
- 仕様の持ち主が決めた後は、担当者の番に戻る。本人から見た窓口を担当者に一本化する。
- AI から担当者へ渡るときは、必ず材料と案を添える。本人が答えを待たずに送った場合も同じ。
- 入力（置き場所の質問、マスの必須の質問、問いの確認）は省けない。入力が足りないまま担当者に渡すと、伝える費用が聞き返しに移るだけで下がらない。本人が省けるのは、AI の答えを読んで自分で確かめる手順だけ。どの質問も「わからない」で進められるが、すべてに「わからない」と答えた場合は、状況を一言書いてもらう。
- 入力を省けるのは2つの場合だけ。AI が失敗した場合（その時点の内容で送れる）と、業務が止まっている場合（マスごとの詳しい質問を省く）。

## 8. 規則

形だけを定義し、日数や時間は設定で変えられる値とする。

| 規則 | 内容 | 設定で変える値 |
| --- | --- | --- |
| 期限 | 期限を守れたかは、対応する側の番の時間だけで判定する。本人の返事を待つ時間は含めない。測るのは「最初の反応まで」と「結果を伝えるまで」の2つ。あわせて、本人が書いてから終わるまでの全体の時間も記録する（判定には使わず、振り返りに使う） | マスごとの目安の時間。緊急度による短縮 |
| 緊急度 | 種類とは別に持つ。通常、急ぎ、業務が止まっているの3段階。本人が申告し、担当者が直せる。AI は文面から申告を補う。「業務が止まっている」は、AI の調査を待たずに担当者の番にする | 段階ごとの期限と通知先 |
| 返事がないとき | 終える前に、1度だけ本人に知らせる。結果を伝えた後なら回答済み、聞き返した後なら取り下げで終える（答えを返していないため） | 知らせるまでの期間、終えるまでの期間 |
| 開き直し | 終わった件に本人が追記すると、担当者の番で開き直す。期間を過ぎた追記は新しい問い合わせとして受け、前の件を結びつける | 開き直せる期間 |
| 引き継ぎ | 担当者が替わっても、相談しても、本人に同じことを聞き直さない。引き継ぐ人は記録を読めば足りる | — |
| 入力の途中で止まった件 | 答えを返す前に本人が離れた件は、期間が過ぎたら取り下げにする | 取り下げにするまでの期間 |
| 言語 | 言葉の違いは、伝える費用そのもの。画面の文言と選択肢は複数の言語で持つ。AI は本人の言語でやり取りし、担当者には訳を添える。本人が書いた原文は必ず残す。根拠の引用は、資料の原文のまま示す | 使う言語の一覧、既定の言語 |

## 9. 測るもの

4つの課題それぞれに、費用が下がったかを見る指標を置く。課題に結びつかない数字は測らない。

見出しにする指標は3つ。

| 指標 | 何が分かるか |
| --- | --- |
| どの段で終わったか | AI と本人で終わった割合、担当者で終わった割合、相談に上がった割合。「担当者で完結」の達成度そのもの |
| 開き直された割合 | 答えや対応が、実際には足りていなかった度合い |
| 期限を守れた割合 | 担当者の番で止まっていないか |

課題ごとの指標。

| 課題 | 指標 |
| --- | --- |
| 伝える費用 | 担当者が本人に聞き返さずに判断できた割合。入口にかかった時間。「わからない」「文章で書く」が選ばれた割合（質問ごと）。言い直しを作り直した回数 |
| 待つ費用 | 期限を守れた割合。本人が書いてから終わるまでの全体の時間 |
| 届け先を誤る費用 | AI が置いたマスを担当者が置き直した割合。担当者が途中で替わった回数 |
| 繰り返す費用 | 相談に上がった割合。先例を使って担当者のところで終わった件の数。マスごとの件数の推移 |
| 全体: 用は足りたか | 終わり方の内訳。終わった後に開き直された割合 |

- **問い合わせの件数は目標にしない。** 件数を目標にすると、入口を狭くする力が働く。件数は、マスごとの偏りを見て直す場所を探すために使う。
- **解決済みの割合は見出しにしない。** 本人が解決を伝えるかどうかは習慣による。足りなかった場合に本人が戻ってくることのほうが、実態に近い。

## 10. まだ決めていないこと

枠組みとして残っている論点はない。作るものと、いま決められない点（保存期間、期限の目安の値）は `requirements.md` にある。

## 11. いまの骨組みとの差分

最初の版（実装の順番の1〜3と、返事がないときの決まり）は、骨組みとして入った。流れ、状態、スキルの置き場所と受け渡す型は動く。資料、利用者、先例は見本で、担当者向けのスキル（助言、下書き、訳）は見本の実装だけを持つ。各要件の実装状況は `requirements.md` の表の右端の欄にある。

枠組みに対して、いまの骨組みに残っている差は次のとおり。

| 枠組み | いまの骨組み | 差 |
| --- | --- | --- |
| 入口は、押して答える一問一答。文章でも書ける | そのとおり | — |
| 種類は5つ。障害は緊急度。置き場所はシステム × 機能 × 種類 | そのとおり | 種類の行を、設定だけで足すことはできない（コードに書かれている） |
| 状態は区間 × 誰の番か。終わり方は4つ。結果は本人が確かめる | そのとおり。番は、本人、AI、担当者、仕様の持ち主 | 担当者の区別がない（「担当者の番」は、担当者の誰かの番） |
| 担当者に渡る前に入力が揃っている。答えを待たずに送っても、調査は裏で行う | そのとおり | 裏での調査は、API を止めると失われる（やり直す手段はない） |
| 担当者に、AI が材料、判断の案、手順の案、下書きを出す | そのとおり。材料は、出どころごとに欄を分けている | 案、下書き、訳を作る実装は見本。内容の質は確かめていない |
| 具体的な手順を示す。頼まれた作業でも、本人が自分でできる手順があれば示す | 説明が、番号つきの手順を出せる | 手順の中身は、見本 |
| 仕様の持ち主への相談と、先例 | 相談、決定の記録、同じ置き場所の先例を材料と案の根拠に使う、先例の一覧 | 相談が届くのは画面の中だけ（外への通知がない）。後の決定での上書きがない。似ているかの判断は、見本の実装では行っていない |
| 返事がないときは、1度知らせてから終える | そのとおり（結果を伝えた後は回答済み、聞き返した後は取り下げ） | 知らせは画面の中だけ。祝日を扱わない |
| 期限、入力の途中で止まった件、開き直せる期間 | なし | 次の版（実装の順番の4） |
| 測るもの | 状態の履歴と、スキルごとの利用量を記録している | 集計と指標の画面がない（実装の順番の5） |
| 設定として持つ | システムと機能、マスごとの質問と相談先、期間、言語 | 担当者、資料の範囲、期限の目安、設定を画面から変えることは、まだ |
| 変更の記録 | なし | 次の版（実装の順番の6） |
| 言語 | 日本語と英語。書かれた内容は訳さず、担当者には訳を添える | 訳は見本の実装（実際には訳さない） |

### 実装の順番

土台から順に積む。各段階とも骨組みの水準（流れが通り、どこに何を置くかが分かること）で止める。

| 順 | 内容 | 状況 |
| --- | --- | --- |
| 1 | 置き場所と状態の作り替え。種類を5つにし、機能の列と緊急度を足す。状態を区間 × 誰の番かに、終わり方を4つにする。日本語と英語 | 済み |
| 2 | 担当者で完結させる流れ。担当者に材料、判断の案、返信の下書きを出す。担当者が結果を伝え、本人が確かめる。見送り。返事がないときの決まり | 済み |
| 3 | 相談と先例。仕様の持ち主への相談、決定の記録、同じ置き場所の先例を AI が担当者に示す | 済み |
| 4 | 時間が起こす出来事の残り。期限、入力途中の取り下げ、開き直せる期間 | 次の版 |
| 5 | 測るものと、資料を育てる道。3つの見出しの指標、マスごとの集計、FAQ の下書き | 次の版 |
| 6 | 変更の記録。変更を記録し、AI が調査の材料に使い、関係する本人に知らせる | 次の版 |

実際に使い始めるには、これとは別に、社内の環境に合わせた土台（認証、実際の資料の検索、承認された環境のモデル）が要る。骨組みでは、差し替えの境界（検索、モデル、利用者）を用意するところまでを行う。
