# スキルの評価

プロンプト、モデル、設定を変えたときに、スキルの出力が良くなったのか悪くなったのかを数字で比べる。目で見た印象では判断しない。

## なぜ必要か

実際のモデルでプロンプトを調整したとき、少ない回数の出力を目で見て判断し、2回誤った。

- プロンプトの例文と試した問い合わせが同じ題材だったため、例文をなぞっただけの出力を「自然に書けている」と判断した。
- 出力のばらつきが大きい設定のまま5回ずつ試し、同じプロンプトが「5回中0回」にも「5回中4回」にもなった。

評価の仕組みは、この2つを防ぐ決まりを持つ。

さらに、評価の仕組みを作った直後にも1回誤った。

- `temperature` を 0 にすれば毎回同じ出力になると考えたが、同じ条件で評価を2回実行すると、32件中14件で文面が変わり、1件は合否が入れ替わった。同じ入力を続けて呼んだときに出力が揃っていたのを、再現性があると見誤っていた。別の入力を間に挟むと揃わないことがある。

## 決まり

1. **製品と同じコードで測る**: 評価は、製品が使うスキルの実装（入力の組み立て、出力の読み取り、確かめる処理を含む）を呼ぶ。評価用に別の呼び出しを書かない。
2. **出力の揺れを前提にして測る**: `temperature` を 0 にし、乱数の種（`seed`）を固定して測る。それでも出力が完全に再現するとは限らない（下記）。1回の実行で1件だけ変わった合否を、改善や悪化の根拠にしない。判断に使う結果は、繰り返しの回数（`repeat`）を3以上にして、通った割合で表す。
3. **調整に使う例と、確認に使う例を分ける**: 例には `dev`（調整用）と `holdout`（確認用）の区分を付ける。プロンプトを直すときに見てよいのは `dev` の結果だけ。`holdout` は直した後に通った割合を見るだけにし、個々の出力を読んで直す材料にしない。`holdout` の出力を読んで直したら、その例は `dev` に移し、新しい `holdout` を足す。
4. **プロンプトの例文と、評価の例の題材を分ける**: プロンプトに書く例文は、扱う業務と無関係な題材にする（`docs/skill-architecture.md`）。評価の例は、業務の題材で書く。
5. **採点の基準を先に書く**: 出力を見てから基準を決めない。例を足すときに、通る条件を一緒に書く。
6. **結果には条件を残す**: モデル、プロンプトの版、設定、実行日時を結果に記録する。条件の違う結果を比べない。

## 例の置き場所

| 場所 | 内容 | 公開 |
| --- | --- | --- |
| `evals/cases/<スキル>.json` | 作った例。実在の問い合わせを含めない | する |
| `evals/private/<スキル>.json` | 実際の問い合わせから作った例。形式は同じ | しない（`.gitignore`） |
| `evals/reports/` | 実行結果 | しない（`.gitignore`） |

このリポジトリは公開されている。実際の問い合わせ、社内のシステムの名前、顧客の名前を含む例は、必ず `evals/private/` に置く。

## 採点の項目

採点は、機械的に確かめられる条件で行う。例ごとに、通る条件を `expect` に書く。

文章（言い直しの文章、説明、質問文）に使える条件:

| 条件 | 意味 |
| --- | --- |
| `mustInclude` | すべての語を含む |
| `mustIncludeAny` | 語の組ごとに、どれか1つを含む |
| `mustNotInclude` | どの語も含まない |
| `mustNotMatch` | どの正規表現にも当てはまらない |
| `minSentences`、`maxSentences` | 文の数（「。」で数える） |
| `style` | `plain`（「である」調。文末が「です・ます」でない）、`polite`（「です・ます」調） |

スキルごとの条件:

| スキル | 条件 |
| --- | --- |
| 受付 | `category`（または `categoryAnyOf`）、`systemId`（または `systemIdAnyOf`。`null` は「推測しない」が正解であることを表す） |
| 聞き手 | `minQuestions`、`maxQuestions`、`forbidLocationQuestion`（場所を尋ねる質問がない）、`forbidEngineerTerms`（エンジニアでなければ答えられない語がない）、質問文への `mustNotMatch`。選択肢の数（0個、または2〜4個）はすべての例で確かめる |
| 言い直し | 言い直しの文章（`summary`）への上の条件。ただし `mustNotInclude` と `mustNotMatch` は、`goal`、`whatHappened`、`expectedResult` にも適用する。これらの項目は担当者への引き継ぎと調査に使うため、言い直しの文章に出ていなくても、本人が言っていないことが足されていれば落とす |
| 説明 | `answersQuestion`（問いに答えられたかの判定）、`mustAcknowledgeUnknown`（「確認できませんでした」と述べている）、説明への上の条件。コード上の名前（英字の識別子）が出ていないことは、すべての例で確かめる |

例のファイルに知らない条件の名前が書かれていたら、実行を止める。書き間違えた条件が、確かめられないまま通ることを防ぐため。

### 機械的な採点の限界

語を含むか含まないかで確かめるため、次のことは測れない。

- 文章の自然さ、読みやすさ
- 条件に書いていない書き足しや言い換えの誤り

「本人が言っていないことを足していないか」は、例ごとに「足されやすい語」を `mustNotInclude` に書いて確かめる。書いていない語が足されても検出できない。意味の正しさを判定させる採点（別のモデルに読ませる方式）は、Claude をつないだ段階で加える。それまでは、結果の一覧で `dev` の出力を人が読んで補う。

## 実行

```bash
npm run eval -- -Pskill=restater                 # 1つのスキルの dev を測る
npm run eval -- -Pskill=all -Psplit=holdout      # 全スキルの holdout を測る
npm run eval -- -Pskill=restater -PpromptVersion=v2 -Plabel=v2 -PcompareWith=<前回の結果のフォルダ>
```

| 引数 | 意味 | 既定 |
| --- | --- | --- |
| `skill` | `reception`、`interviewer`、`restater`、`explainer`、`all` | `all` |
| `split` | `dev`、`holdout`、`all` | `dev` |
| `cases` | `public`、`private`、`all` | `public` |
| `promptVersion` | プロンプトの版 | `v1` |
| `model`、`think`、`temperature` | モデルと設定。指定しなければ `local-ai` の設定 | — |
| `repeat` | 1つの例を繰り返す回数 | `1` |
| `label` | 結果のフォルダの名前に付ける語 | なし |
| `compareWith` | 比べる相手の結果のフォルダ | なし |

実際のモデルを呼ぶため、Ollama が動いている手元でだけ実行する。通常の検証（`npm run verify`）と CI には含めない。採点の処理そのもの（条件の判定）は、通常の検証で単体テストする。

## 結果

`evals/reports/<日時>-<label>/` に、`report.md`（人が読む）と `results.json`（比べるための記録）を出す。

`report.md` の内容:

1. 条件（モデル、プロンプトの版、設定、区分、実行日時）
2. スキルごとのまとめ（例の数、通った数と割合、条件ごとの落ちた数、応答時間の中央値と最大、トークン数）
3. 落ちた例の一覧（入力、出力、落ちた条件）
4. すべての例の出力（`dev` のみ）

`holdout` を測ったときは、3 に入力と落ちた条件の名前だけを出し、出力は出さない。4 も出さない。出力を読んで直す材料にしないため。

`compareWith` を指定したときは、スキルごとの通った割合の差と、結果が変わった例（通るようになった例、落ちるようになった例）を出す。

## 結果の読み方

- 例は1スキルあたり十数件で、1件の違いが数ポイントの差になる。小さな差で優劣を決めない。
- `dev` で良くなり `holdout` で良くならない変更は、`dev` の例に合わせただけの可能性が高い。採用しない。
- 通った割合が上がっても、落ちるようになった例があれば内容を確かめる。別の種類の誤りが増えていることがある。
- 例が足りないと感じたら、プロンプトを直す前に例を足す。
