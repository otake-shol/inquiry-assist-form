# スキルの構成

AIに任せる仕事を8つのスキルに分ける。スキルを呼ぶ順序と、機械的に確かめられること（根拠の照合、案の確認、訳の数の確認）は、通常のコードが担う。図と考え方は公開ページ（`site/index.html`）にある。この文書は、実装の仕様を定める。

この文書は、いまの仕様だけを書く。画面と API の間の決まりは `api-contract.md` が正。

## 分ける基準

スキルは、次のどれかが違う単位で分ける。どれも変わらない分割はしない。

- **品質の基準**: 何をもって良い出力とするか
- **使える道具**: 一次情報の検索を使うか、どこまで使うか
- **失敗のしかた**: 失敗したときに本人と担当者に何が起きるか

## スキルの一覧

インターフェースは `dev.inquiryassist.core.skill` に置き、Spring にも HTTP にも依存させない。実装は、スキルごとに別のクラスにする。このリポジトリが持つ実装は、8つともモックだけ（「実装の切り替え」の節）。

| スキル | 識別子 | 読み手 | 仕事 | 道具 |
| --- | --- | --- | --- | --- |
| 受付 | `reception` | — | 本人の文章から、まだ決まっていない置き場所（種類、システム、機能）を読み取る | なし |
| 聞き手 | `interviewer` | 本人 | 足りない情報だけを本人に聞く。設定の質問のうち、文章に答えが書かれているものを読み取る。設定に質問がなければ、質問を作る | 用語対応表と FAQ の軽い検索 |
| 言い直し | `restater` | 本人 | 置き場所、質問と答え、本人の文章から、問いを組み立てる。作り直しも担う | 用語対応表 |
| 調査 | `investigator` | — | 一次情報を調べ、根拠つきの事実を集める | 読み取り専用の検索とファイルの読み取り（繰り返し使う） |
| 説明 | `explainer` | 本人 | 確かめられた事実だけから、本人向けの説明と、本人が自分で行える手順を書く | 用語対応表 |
| 助言 | `advisor` | 担当者 | 確かめられた事実と、同じ置き場所の先例から、判断の案（相談が要るかを含む）と、作業の手順の案を作る | なし（自分では調べない） |
| 下書き | `drafter` | 本人（担当者が確かめる） | 担当者が本人に送る文章（聞き返し、結果）の下書きを作る | なし |
| 訳 | `translator` | 担当者 | 本人の言語で書かれた文章を、担当者の言語に訳す | なし |

識別子は列挙型 `Skill` で持ち、スキルの実行記録（`trace[].skill`）にこの値を使う。言い直しの作り直しは、`restater` として記録する。

種類は5つ（`InquiryType`: `HOW_TO`、`HOW_IT_WORKS`、`LOOKS_WRONG`、`DO_FOR_ME`、`CHANGE_REQUEST`）。障害は種類ではなく、問い合わせの緊急度（`NORMAL`、`HURRY`、`BLOCKED`）として持つ。緊急度は本人が申告するもので、AI が文章から決めるものではない。

### 担当者向けの3つを、本人向けと分ける理由

- **助言を、説明と分ける**: 読み手が違う（説明は本人に、業務の言葉で、事実だけを書く。助言は担当者に、技術の言葉で、事実から先の「案」を書く）。品質の基準が違う。失敗のしかたも違う（助言が失敗しても、誰も止まらない。担当者は案なしで進められる）。
- **下書きを、助言と分ける**: 読み手が違う（本人）。呼ぶ時点も違う（助言は材料が揃った時点で裏で作る。下書きは、担当者が頼んだときに、担当者が決めた方向に沿って作る）。
- **下書きを、説明と分ける**: 入力が違う（担当者の意図と、それまでのやり取りを受け取る）。説明は「確かめられた事実だけから書く」ことが品質の基準だが、下書きは担当者の判断を伝える文章で、事実にないこと（担当者が決めたこと）を含む。
- **訳を、ほかと分ける**: 品質の基準が違う。訳は、原文の意味を変えない、足さない、省かないことが基準で、何かを判断したり、書き直したりしない。失敗のしかたも違う（失敗しても、原文は見えている）。

## インターフェース

```java
interface ReceptionSkill {
    AiResult<Reception> receive(String utterance, List<SystemOption> candidates, Placement decided);
}

interface InterviewerSkill {
    // 質問を作る
    AiResult<Interview> ask(String utterance, InquiryType type, SystemOption system, FunctionOption function,
            AccessScope scope, String language);
    // 設定の質問のうち、文章に答えが書かれているものを読み取る
    AiResult<Prefill> prefill(String utterance, List<IntakeQuestion> questions);
}

interface RestaterSkill {
    AiResult<StructuredInquiry> restate(String utterance, InquiryType type, SystemOption system, FunctionOption function,
            List<AnsweredQuestion> answers, List<String> corrections, String language);
}

interface InvestigatorSkill {
    AiResult<Investigation> investigate(StructuredInquiry inquiry, AccessScope scope, ProgressListener progress, String language);
}

interface ExplainerSkill {
    AiResult<Explanation> explain(StructuredInquiry inquiry, List<Finding> confirmedFindings, String language);
}

interface AdvisorSkill {
    AiResult<Advice> advise(StructuredInquiry inquiry, InquiryType type, List<Finding> confirmedFindings,
            List<PrecedentNote> precedents, String language);
}

interface DrafterSkill {
    AiResult<Draft> draft(DraftRequest request);
}

interface TranslatorSkill {
    AiResult<Translation> translate(List<String> texts, String from, String to);
}
```

- 言い直しの作り直しは、別のメソッドにしない。本人が伝えた違う点（`corrections`。伝えられた順）を足して、最初から言い直す。前回の言い直しの文章は渡さない。前回の文章を渡すと、直すべき記述がそこに残っているため、訂正と食い違う文になりやすい（手元のモデルで試して、確かめた）。`corrections` が空なら、最初の言い直し。
- 聞き手の2つの仕事（質問を作る、答えを読み取る）は、「足りない情報だけを本人に聞く」という同じ役割の2つの面なので、1つのスキルにまとめる。品質の基準（聞かなくてよいことを聞かない）も、失敗のしかた（失敗しても先へ進める）も同じ。実際のモデルで動かすときは、指示文と出力の形が違うので、指示文は分ける。
- 言語（`language`）は、呼ぶ側が渡す。スキルは、自分では言語を決めない（「言語」の節）。

## 受け渡す型

| 型 | 中身 | 不変条件 |
| --- | --- | --- |
| `Reception` | `type`、`systemId`、`functionId`。読み取れないものは `null` | — |
| `Interview` | `questions`（詳しい質問） | 最大3個 |
| `Prefill` | `answers`（質問の id と、選択肢の id または文章） | — |
| `StructuredInquiry` | `summary`（言い直しの文章）、`type`、`targetSystem`、`goal`、`whatHappened`、`expectedResult` | `summary` と `goal` は必須 |
| `Finding` | `statement`（事実の一文）、`evidence`（その事実の根拠となる出典） | `evidence` は1件以上。根拠を挙げられない内容は事実にせず、「見つからなかったこと」か「次に確認すること」に入れる |
| `Investigation` | `findings`、`notFound`、`nextChecks` | — |
| `VerifiedInvestigation` | `confirmed`、`unconfirmed`、`notFound`、`nextChecks`、出典ごとの照合の結果 | `confirmed` の各事実の `evidence` は、照合を通った出典だけ |
| `Explanation` | `text`（本人向けの説明）、`answersQuestion`（確かめられた事実が、本人の問いに答えているか）、`steps`（本人が自分で行える手順。それぞれ `action` と `check`。なくてもよい） | `text` は空でない。`steps` は10個まで |
| `PrecedentNote` | 先例のうち、助言に渡す部分（状況、決定の種類、決定の内容、理由）。決めた人の名前と、元の問い合わせは渡さない | — |
| `Advice` | `judgment`（判断の案。なくてもよい）、`procedure`（手順の案。なくてもよい） | — |
| `Advice.Judgment` | `text`、`needsConsultation`（仕様の持ち主への相談が要りそうか）、`consultationReason`、`basedOn`（基づく事実の番号）、`basedOnPrecedents`（基づく先例の番号）。番号は、渡した並びの、1から始まる番号 | `text` は空でない |
| `Advice.Procedure` | `steps`（それぞれ `target`（対象）、`action`（操作やコマンド）、`check`（結果の確かめ方））、`rollback`（元に戻す方法。なければ `null`）、`basedOn`、`basedOnPrecedents` | `steps` は1件以上 |
| `DraftRequest` | `kind`（`ASK` 聞き返し／`RESULT` 結果）、`inquiry`、`confirmedFindings`、`judgment`（判断の案の文章。あれば）、`decision`（その問い合わせについての、仕様の持ち主の決定。あれば）、`messages`（それまでのやり取り）、`note`（担当者が伝えたいこと。任意）、`language`（本人の言語） | `kind` は必須 |
| `Draft` | `text`（下書きの文章） | 空でない |
| `Translation` | `texts`（訳した文章。渡した順） | — |

`Finding` が事実と根拠を対にして持つことが、この構成の要になる。事実と出典を別々の一覧で持つと、ある出典が照合で落ちたときに、どの事実が根拠を失ったのかが分からない。対にしておけば、根拠を失った事実だけを機械的に外せる。

## いつ呼ぶか

スキルを呼ぶ順序は、通常のコードが決める（`InquiryService`、`AnswerPipeline`、`InvestigationRunner`、`AdviceRunner`）。スキル同士に相談させない。次に何が起きるかが決まっているほうが、待ち時間も費用も読める。

| スキル | いつ呼ぶか | 入力 | 出力 |
| --- | --- | --- | --- |
| 受付 | 本人が文章を書いたときだけ（最初から文章で始めた、途中で切り替えた）。押して答えただけなら、呼ばない | 文章、システムと機能の候補、本人が既に選んだ置き場所 | まだ決まっていない置き場所。読み取れないものは `null` |
| 聞き手（答えを読み取る） | マスの設定に詳しい質問があり、本人が文章を書いているとき | 本人の文章、設定の質問（id、質問文、選択肢） | 文章に答えが書かれている質問の、id と答え |
| 聞き手（質問を作る） | 置き場所の質問が終わり、マスの設定に詳しい質問がないとき | 種類、システム、機能、本人の文章（なければ、ない旨） | 質問（0〜2個） |
| 言い直し | 入口の質問を終えたとき。作り直すとき | 置き場所、詳しい質問と答え、本人の文章、本人が後から直したこと | 組み立てた問い |
| 調査 | 問いを確かめた時点（調べる種類のとき）。担当者に渡した後にも、裏で呼ぶ（下の「調査から説明までの順序」） | 確かめた問い、本人の閲覧権限 | 事実と根拠の対、見つからなかったこと、次に確認すること |
| 説明 | 照合の後、確かめられた事実が1件以上あるとき | 確かめた問い、確かめられた事実 | 説明、問いに答えているかの判定、手順 |
| 助言 | 担当者の番の問い合わせに、確かめられた事実か、同じ置き場所の先例が1つ以上あり、案がまだないとき（裏で） | 問い、種類、確かめられた事実、先例 | 判断の案、手順の案 |
| 下書き | 担当者が頼んだときだけ | 問い、確かめられた事実、判断の案、決定、やり取り、担当者が伝えたいこと | 下書きの文章 |
| 訳 | 担当者が頼んだときだけ（本人の言語と、担当者が見ている言語が違うとき） | 本人の言語で書かれた文章 | 訳した文章 |

種類ごとの経路（調べるか、答えの後にどうなるか）は、`InquiryType` に集約する。経路の表は `api-contract.md` の「種類ごとの経路」が正。

- 受付は、本人が既に選んだ置き場所を変えない。モデルの出力にかかわらず、選んだ値を使う。候補にない id は null にする。機能は、決まったシステムの機能でなければ null にする。
- 答えの読み取りは、出力を信用しない。選択肢は、その質問の選択肢にあるものだけを採る。文章で答える質問は、返された答えが本人の文章の中にそのまま含まれている場合だけ採る（空白の違いは無視する）。この確かめは、聞き手の実装ではなく、入口の処理（`core/intake`）が行う。モックでも実際のモデルでも同じ確かめを通すため。
- 受付が失敗しても、エラーにしない。置き場所は置かれず、質問として聞く。押して答える入口は、AI なしでも最後の質問まで進める。
- 言い直しは、読み取れた目的を文章に含める（「〜したいので、〜を知りたい」）。読み取れなければ、作らない。
- 種類が決まっていない（本人が「わからない」と答え、受付も置けなかった）場合も、言い直しは呼ぶ。調査は、種類が決まっていない場合は `HOW_IT_WORKS` と同じ経路で行う。

## 調査から説明までの順序

調査、照合、説明の順に進める。この部分は `core` の `AnswerPipeline` にまとめ、Spring なしでテストできるようにする。

1. **調査**（AI）: `Investigation` を返す。進捗は調査のスキルが通知する。
2. **照合**（コード）: 出典ごとに実在を確かめ、事実を2つに分ける。
   - 根拠が1件でも照合を通った事実は `confirmed`。`evidence` は通った出典だけに絞る。
   - 根拠がすべて落ちた事実は `unconfirmed`。
3. **説明**（AI）: `confirmed` が1件以上あるときだけ呼ぶ。渡すのは `confirmed` だけで、`unconfirmed` は渡さない。説明のスキルは、確かめられなかった内容を知る手段を持たない。

進捗には、調査の通知に続けて「根拠を確かめています」と、説明を呼ぶ場合は「答えをまとめています」を加える。

結果は次のように組み立てる。

| 項目 | 中身 |
| --- | --- |
| `grounded` | `confirmed` が1件以上あるか |
| `answered` | `grounded` で、かつ説明のスキルが「問いに答えている」と判定したか。確かめられたが的外れな事実しか集まらなかった場合に、それを答えとして見せないために持つ。この判定は機械的に確かめられないため、モデルの判定に頼る。ただし判定が効くのは「答えとして見せない」方向だけで、誤って `true` になっても従来と同じ表示になるだけで済む |
| `askerExplanation` | 説明のスキルの出力。`grounded` でなければ `null` |
| `citations`（本人向け） | `confirmed` の事実の根拠（照合を通ったもの） |
| `memo.findings` | `confirmed` の事実の文 |
| `memo.unconfirmed` | `unconfirmed` の事実の文。担当者にだけ「根拠を確かめられなかったこと」として示す |
| `memo.notFound`、`memo.nextChecks` | 調査の出力のまま |

確かめられなかった事実を捨てずに `memo.unconfirmed` に残すのは、担当者にとっては調べる手がかりになるため。ただし事実としては示さず、必ず区別して表示する。

問い合わせた本人には見せない。本人は裏づけのない内容の真偽を判断できず、もっともらしい文面であればそのまま試してしまう。本人向けの応答には API の時点で含めず、画面での非表示には頼らない。

### 裏での調査

調査（調査、照合、説明の一続き）を呼ぶ場所は、本人が待っている間だけではない。担当者に渡した後にも、裏で呼ぶ（答えを待たずに送った件、業務が止まっている件、時間切れになった件）。呼ぶ場所は増えるが、`AnswerPipeline` を実行して結果を保存する役は1か所にまとめ、結果を誰に見せるかは、終わった時点の問い合わせの状態で決める（`api-contract.md` の「調査の状況と、裏での調査」）。スキルの側は、裏で呼ばれたかどうかを知らない。

- 本人が待つ調査が時間切れ（既定60秒）になったら、打ち切らずに担当者へ引き継ぎ、調査は裏で続ける。本人には、失敗ではなく引き継ぎとして伝える。
- 裏での調査の失敗は、本人には見せない。担当者に、失敗したことだけを示す。
- 調査は、問いを確かめた時点で API が始める。画面が進捗を見ているかどうかに、関係しない（`api-contract.md` の 5 と 6）。

### 説明が出す手順

「使い方を知りたい」と「やってほしい」では、本人が知りたいのは、何をどの順に行えばよいか。説明のスキルは、確かめられた事実から操作の順に並べられる場合に、文章の説明に加えて、手順（`steps`）を出す。

- 手順は、行う順に並べる。それぞれ `action`（何をするか。画面の名前、押す場所、入力する値をできるだけ具体的に）と、`check`（結果の確かめ方。なければ `null`）を持つ。
- 手順も、説明と同じく、確かめられた事実だけから書く。事実から手順を組めなければ、出さない（空のまま）。無理に作らない。
- 新しいスキルにはしない。品質の基準（確かめられた事実だけから、本人に向けて、業務の言葉で書く）も、道具も、失敗のしかたも、説明と同じため。出力の形が1つ増えるだけ。
- 問いに答えていない説明（`answersQuestion` が `false`）の手順は、コードが捨てる（答えの型 `ZeroAnswer` が、問いに答えていない答えに手順を持たせない）。答えになっていない手順を、本人が試さないようにするため。
- 担当者向けの手順の案（助言の `procedure`）とは別のもの。こちらは本人が自分で行う操作で、本人に見せる。助言の手順は担当者が行う作業で、担当者だけに見せる。
- モックの説明は、種類が `HOW_TO` か `DO_FOR_ME` のときに、決まった手順を返す。

## 担当者向けの3つのスキル

担当者に渡った件で、AI が担当者を支える。目指すのは、担当者が自分のところで終わらせられる件を増やすこと。

### 助言

確かめられた事実に加えて、同じ置き場所の先例（仕様の持ち主が下した決定の記録）を受け取り、判断の案と、手順の案を作る。

- **先例を探すのは、コード**（`PrecedentFinder`）。同じ置き場所（システムと種類が同じ）の先例を、機能が同じものを先にして、新しい順に5件まで引く。似ているかどうかの判断は、助言に任せる（渡された先例のうち、当てはまるものだけを案の根拠にする）。先例は言語を問わずに引き、書かれた言語のまま渡す。
- 助言に渡す事実は、照合を通ったものだけ。確かめられなかった内容は、渡さない。
- **案は、コードで確かめてから保存する**（`core` の `AdviceVerifier`）。事実の番号と先例の番号のそれぞれについて、存在しないものを外す。外した結果、どちらも空になった案（判断の案、手順の案のそれぞれ）は捨てる。基づくものがない案は、出さない。
- 案が、事実や先例から正しく導かれているかは、機械的には確かめられない。そのため、担当者の画面では、案を事実と区別して示し、基づく事実と先例を並べて見せる。決めるのは担当者。
- 呼ぶきっかけは2つ。調査の結果を保存した時点で、担当者に渡っている（裏での調査が終わった、答えの完了と同時に担当者に渡った）。または、材料を持つ問い合わせが、担当者に渡った（本人が「解決していない」と答えた、など）。本人が待っている間は呼ばない（本人の待ち時間を延ばさない）。
- 案を作った後に新しい先例ができても、案は作り直さない。
- 調べない種類（変えてほしい）の件でも、先例があれば案が出る。
- 先例は、人が下した決定なので溜める。AI の答えと案は溜めず、毎回作り直す。

### 下書き

担当者が頼んだときだけ、本人に送る文章の下書きを作る（`api-contract.md` の「担当者の操作」）。

- 担当者が決めた方向（聞き返すのか、結果を伝えるのか）と、担当者が伝えたいこと（`note`）に沿って書く。その問い合わせについての決定（仕様の持ち主が決めたもの）があれば、それを渡す。担当者が伝える結果の中心は、決定の内容になるため。
- 結果は保存しない（担当者の入力欄に入るだけ。送られた文章は、担当者の発言として残る）。利用量は記録する。
- AI が直接送ることはない。

### 訳

本人の言語と、担当者が見ている言語が違う場合に、担当者が頼むと、本人の言語で書かれた文章を訳す。

- **コードで確かめること**: 返ってきた文章の数が、渡した数と同じであること。違えば、失敗として扱う（どの訳がどの原文のものか、分からなくなるため）。確かめるのは、スキルの実装ではなく、呼ぶ側。訳の中身が正しいかは、機械的には確かめられない。そのため、訳は必ず原文に添えて出し、原文を置き換えない。
- 訳した文章は、保存しない。頼まれるたびに訳す。
- **訳さないもの**: 根拠の引用（資料の原文のまま示す決まり）。設定の名前と画面の文言（言語ごとに持っている）。担当者が書いた文章と、AI の案（担当者の言語の側にある）。
- **本人には見せない。** 訳は担当者のためのもの。本人のページには、書かれたときのままの文章だけを出す。
- 逆の向き（担当者から本人へ）は、下書きが担う。担当者が「伝えたいこと」を自分の言語で書けば、下書きが本人の言語の文章にする。

## 言語

AI は、本人の言語（問い合わせの `language`。`api-contract.md` の「言語」の節）で書く。

- 呼ぶ側（`InquiryService` と `AnswerPipeline`）が、スキルに渡す入力に本人の言語を加える。スキルは、自分では言語を決めない。
- 人が読む文章を書くスキル（聞き手の質問づくり、言い直し、調査、説明）が、この言語で書く。受付と、聞き手の読み取りは、識別子だけを返すので言語に関わらない。
- スキルに渡す設定の名前（種類、システム、機能、質問、選択肢）は、本人の言語の名前。
- 根拠の引用は訳さない。照合（`InvestigationVerifier`）は、引用が資料に書かれたとおりかを確かめるため、訳した引用は照合で落ちる。
- 助言は、既定の言語で書く（読み手は担当者。担当者ごとの言語は、書く時点では分からない）。下書きは、本人の言語で書く（送る相手は本人）。

**分かっている制約**

- 本人の文章が、本人の言語（画面の言語）と違う言語で書かれていても、文章の言語は見ない。
- 資料と違う言語の問いから、資料を探せるかは、実際のモデルをつなぐときに確かめる。

## 失敗したときの扱い

スキルごとに、失敗が人に与える影響を変える。

| 失敗したスキル | 扱い | 理由 |
| --- | --- | --- |
| 受付 | エラーにしない。置き場所は置かれず、質問として本人に聞く | 押して答える入口は、AI なしでも最後の質問まで進める |
| 聞き手 | 質問なしで先へ進む。失敗は、ログと利用量の記録に残す | 質問は答えを良くするための補助で、なくても進められる。本人を止めない |
| 言い直し | エラーを返す。本人は、やり直すか、その時点の内容で担当者に送る。業務が止まっている件は、エラーにせず担当者に渡す | 言い直しがないと、問いを確かめられない。こちらの失敗を理由に、本人を止めない |
| 調査（本人が待っている間） | 進捗ストリームで失敗を伝える。本人は、やり直すか、担当者に送る。何もしなければ、時間切れで担当者に渡る | AI の番のまま、誰にも見えない件を残さない |
| 調査（裏で） | 本人には見せない。担当者に、失敗したことだけを示す。やり直す手段はない（担当者は、材料なしで進める） | 担当者は、材料がなくても判断できる |
| 説明 | 調査と照合の結果（技術メモ、出典）を保存したうえで、失敗として扱う | 費用をかけた調査の結果を失わない。担当者に渡れば、調査の内容が届く |
| 助言 | 案なしで進める。担当者のパネルに、失敗したことだけを示す | 案は補助で、なくても担当者は判断できる |
| 下書き | 担当者にエラーを返す。担当者は、自分で書く | 同上 |
| 訳 | 担当者にエラーを返す。原文は、見えたまま | 訳は原文に添えるもので、なくても読める |

説明が失敗した後にやり直す場合は、調査からやり直す。調査の結果を使い回す仕組みは、実際のモデルをつなぐときに、費用を見て判断する。

## 実装の切り替え

どのスキルをどの実装で動かすかは、スキルごとの設定で決める。全体をまとめて切り替える設定は持たない。

```yaml
inquiry:
  skills:
    reception:    { provider: mock }
    interviewer:  { provider: mock }
    restater:     { provider: mock }
    investigator: { provider: mock }
    explainer:    { provider: mock }
    advisor:      { provider: mock }
    drafter:      { provider: mock }
    translator:   { provider: mock }
  knowledge:
    provider: mock                        # 一次情報の検索
```

- **このリポジトリが持つ実装は、モックだけ。** `provider` に `mock` 以外を指定すると、起動を止める。骨組みの目的は、スキルの置き場所と受け渡しを示すことで、スキルの中身（指示文の品質、実際の資料の検索）を作り込む場所ではないため。
- **`provider` の設定は、実際のモデルの実装を足すときの差し込み口。** 足すときは、スキルのインターフェース（`core/skill`）を実装し、`provider` の値を増やす。受け渡す型、コードで確かめること、失敗したときの扱いは、この文書のとおりに使える。一次情報の検索（`KnowledgeSearch`）と、閲覧権限（`AccessScope`）も、同じく差し替えの境界。
- 「モックで動いているか」は、Spring のプロファイルではなく、この設定から判断する。1つでも `mock` があれば「モックを含む」として扱う。
  - `GET /api/config` の `mock` は、1つでも `mock` があれば `true`。あわせて `skills`（スキルの識別子から、実装の名前への対応）を返す。
  - 問い合わせの記録の `mock` は、その問い合わせで呼んだスキルのうち、1つでもモックなら `true`。一部でもモックの結果が混ざった記録を、実際のモデルの記録として数えないため。
  - 本番（プロファイル `production`）では、スキルか一次情報の検索に、1つでも `mock` があれば起動を止める。実際のモデルの実装を足すまで、本番には出せない。
- モックは、スキルごとに別のクラスにする。本人の文章のキーワードとタグの解釈は、共通の補助クラスにまとめる。タグの一覧は `api-contract.md` の「モックのシナリオ」が正。
- モックの調査は、問いの内容にかかわらず、決まった結果（見本の資料 `mock-knowledge/` にある、求人の掲載期限についての事実）を返す。照合は、見本の資料を実際に読んで、引用が書かれているとおりかを確かめる。

## 実際のモデルをつなぐときに、引き継ぐこと

以前は、本人向けの5つのスキルを手元のモデル（Ollama）で動かす実装と、評価の仕組みを、このリポジトリに持っていた。骨組みの位置づけに合わないので外した（`status.md` の「一度足して、削った機能」）。そこで分かったことのうち、実際のモデルをつなぐときに効くものを、ここに残す。当時の実装と文書は、コミット `c80b4c9` で読める。

**呼び出し**

- スキルごとに、モデルと effort を設定で持つ。受付と聞き手は小さいモデルで足りる。体験の要は言い直しで、待たせられない（本人の確認の場面のため）。説明は、調査の進捗の表示の中で動くので、遅くても体験を損なわない。
- 出力の形は、API の構造化出力で縛る。縛れない場合は、形の崩れた出力を1回だけ呼び直し、それでも崩れていれば失敗として扱う。
- モデルの出力を、そのまま信用しない。選択肢や識別子は、候補にあるものだけを採る。本人が既に選んだ値は、出力にかかわらず、選んだ値を使う。この確かめは、スキルの実装ではなく、呼ぶ側（`core`）に置く（モックでも実際のモデルでも、同じ確かめを通すため）。
- 本人の文章も、資料の本文も、信頼できない入力として扱う。入力に書かれた指示に従わないことを、指示文に明記する。調査の道具を読み取り専用にしておけば、従ってしまった場合の影響は「誤った事実を返す」までに留まり、その事実も、引用の照合を通らなければ本人には見えない。

**調査**

- 回数の上限、行番号、引用の切り出しは、モデルに任せず、コードで決める。モデルが挙げた引用が、見た行の中に見つからなくても、出典は作る（照合で落ち、担当者にだけ見える）。合否を決めるのは、照合に一本化する。
- 進捗の文言は固定にし、モデルが選んだ検索の語やファイルの名前は出さない（内部の言葉が、画面に出るのを避ける）。

**指示文と評価**

- 指示文はファイルに置き、版を持つ。変えるときは、新しい版のファイルを足し、評価で前の版と比べる。
- 指示文の例文は、扱う業務と無関係な題材で書く。業務に近い例文は、言葉や内容が出力に紛れ込み、評価でも「例文をなぞっただけの出力」が良く見えてしまう（実際に起きた）。
- 評価の例は、スキルごとに持ち、品質の基準に対応する項目で採点する。指示文を直すときに見てよいのは、調整用の例の結果だけ。確認用の例は、直した後に、通った割合を見るだけにする。
- 出力は、同じ条件でも揃わない（`temperature` を 0 にし、乱数の種を固定しても、2回の実行で半数近くの文面が変わった）。1回の実行で1件だけ変わった合否を、改善や悪化の根拠にしない。各例を3回以上測り、通った割合で比べる。
- 少ない回数を目で見た印象は、当てにならなかった。品質の判断は、評価の例ができるまで保留する。
- 実際の問い合わせから作った例は、公開しない場所に置く。

**言語**

- 指示文は1つの言語で書き、ほかの言語で書かせるときは、書く言語の指示を足す形にすると、既定の言語のときに送る内容を変えずに済む（評価の結果が、そのまま有効に保てる）。
- 根拠の引用は訳さない（訳した引用は、照合で落ちる）。
