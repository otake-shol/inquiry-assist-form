# スキルの構成

AIに任せる仕事を5つのスキルに分け、呼ぶ順序と根拠の照合は通常のコードが担う。図と考え方は公開ページ（`site/index.html`）にある。この文書は実装の仕様を定める。

## 分ける基準

スキルは、次のどれかが違う単位で分ける。どれも変わらない分割はしない。

- **品質の基準**: 何をもって良い出力とするか
- **使える道具**: 一次情報の検索を使うか、どこまで使うか
- **失敗のしかた**: 失敗したときに本人と担当者に何が起きるか

## スキルの一覧

インターフェースは `dev.inquiryassist.core.skill` に置き、Spring にも HTTP にも依存させない。実装（モック、のちに実際のモデル）はスキルごとに別のクラスにする。

| スキル | 識別子 | 仕事 | 道具 |
| --- | --- | --- | --- |
| 受付 | `reception` | 種別を判定し、対象システムを推測する | なし |
| 聞き手 | `interviewer` | 足りない情報を、非エンジニアが答えられる質問にする | 用語対応表とFAQの軽い検索 |
| 言い直し | `restater` | 言い直しの文章と構造化データを作る。作り直しも担う | 用語対応表 |
| 調査 | `investigator` | 一次情報を調べ、根拠つきの事実を集める | 読み取り専用の検索とファイル読み取り（繰り返し使う） |
| 説明 | `explainer` | 確かめられた事実だけから、本人向けの説明を書く | 用語対応表 |

識別子は列挙型 `Skill` で持ち、利用量の記録（`usages[].step`）にこの値を使う。言い直しの作り直しは `restater` として記録する。

### インターフェース

```java
interface ReceptionSkill {
    AiResult<Reception> receive(String utterance, List<SystemOption> candidates, SystemOption selected);
}

interface InterviewerSkill {
    AiResult<Interview> ask(String utterance, InquiryCategory category, SystemOption system, AccessScope scope);
}

interface RestaterSkill {
    AiResult<StructuredInquiry> restate(
            String utterance,
            InquiryCategory category,
            List<AnsweredQuestion> answers,
            SystemOption system,
            List<String> corrections);
}

interface InvestigatorSkill {
    AiResult<Investigation> investigate(StructuredInquiry inquiry, AccessScope scope, ProgressListener progress);
}

interface ExplainerSkill {
    AiResult<String> explain(StructuredInquiry inquiry, List<Finding> confirmedFindings);
}
```

言い直しの作り直しは、別のメソッドにしない。本人が伝えた違う点（`corrections`。伝えられた順）を足して、最初から言い直す。前回の言い直しの文章は渡さない。前回の文章を渡すと、直すべき記述がそこに残っているため、訂正と食い違う文になりやすい（実際のモデルで確認した）。`corrections` が空なら最初の言い直し。

## 受け渡す型

| 型 | 中身 | 不変条件 |
| --- | --- | --- |
| `Reception` | `category`、`guessedSystemId`（任意） | `category` は必須 |
| `Interview` | `questions` | 最大3個 |
| `Finding` | `statement`（事実の一文）、`evidence`（その事実の根拠となる出典） | `evidence` は1件以上。根拠を挙げられない内容は事実にせず、「見つからなかったこと」か「次に確認すること」に入れる |
| `Investigation` | `findings`、`notFound`、`nextChecks` | — |
| `VerifiedInvestigation` | `confirmed`、`unconfirmed`、`notFound`、`nextChecks`、出典ごとの照合結果 | `confirmed` の各事実の `evidence` は照合を通った出典だけ |

`Finding` が事実と根拠を対にして持つことが、この構成の要になる。事実と出典を別々の一覧で持つと、ある出典が照合で落ちたときに、どの事実が根拠を失ったのかが分からない。対にしておけば、根拠を失った事実だけを機械的に外せる。

## 調査から説明までの順序

調査、照合、説明の順に進める。この部分は `core` の `AnswerPipeline` にまとめ、Spring なしでテストできるようにする。

1. **調査**（AI）: `Investigation` を返す。進捗は調査のスキルが通知する。
2. **照合**（コード）: 出典ごとに実在を確かめ、事実を2つに分ける。
   - 根拠が1件でも照合を通った事実は `confirmed`。`evidence` は通った出典だけに絞る。
   - 根拠がすべて落ちた事実は `unconfirmed`。
3. **説明**（AI）: `confirmed` が1件以上あるときだけ呼ぶ。渡すのは `confirmed` だけで、`unconfirmed` は渡さない。説明のスキルは、確かめられなかった内容を知る手段を持たない。

進捗には、調査の通知に続けて「根拠を確かめています」と、説明を呼ぶ場合は「答えをまとめています」を加える。

結果は次のように組み立てる。

| 項目 | 中身 |
| --- | --- |
| `grounded` | `confirmed` が1件以上あるか |
| `askerExplanation` | 説明のスキルの出力。`grounded` でなければ `null` |
| `citations`（本人向け） | `confirmed` の事実の根拠（照合を通ったもの） |
| `memo.findings` | `confirmed` の事実の文 |
| `memo.unconfirmed` | `unconfirmed` の事実の文。担当者にだけ「根拠を確かめられなかったこと」として示す |
| `memo.notFound`、`memo.nextChecks` | 調査の出力のまま |

確かめられなかった事実を捨てずに `memo.unconfirmed` に残すのは、担当者にとっては調べる手がかりになるため。ただし事実としては示さず、必ず区別して表示する。

問い合わせた本人には見せない。本人は裏づけのない内容の真偽を判断できず、もっともらしい文面であればそのまま試してしまう。本人向けの応答には API の時点で含めず、画面での非表示には頼らない。

## 呼ぶ順序と種別

| 種別 | 受付 | 聞き手 | 言い直し | 調査・照合・説明 |
| --- | --- | --- | --- | --- |
| 仕様確認・相談 | 呼ぶ | 呼ぶ | 呼ぶ | 呼ぶ |
| 不具合の疑い | 呼ぶ | 呼ぶ | 呼ぶ | 呼ぶ |
| 作業依頼 | 呼ぶ | 呼ばない（固定の3問） | 呼ぶ | 呼ばない |
| 障害 | 呼ぶ | 呼ばない（固定の1問） | 「いいえ」で続行する場合だけ呼ぶ | 続行する場合だけ呼ぶ |

本人が種別を仕様確認・相談か不具合の疑いに変更し、聞き手の質問がまだない場合は、その時点で聞き手を呼ぶ。対象システムを変更しただけでは呼び直さない。

## 失敗したときの扱い

スキルごとに、失敗が本人に与える影響を変える。

| 失敗したスキル | 扱い | 理由 |
| --- | --- | --- |
| 受付 | 問い合わせを保存し、エラーと `inquiryId` を返す。本人は「今すぐ担当者に送る」を使える | 種別が分からないと先へ進めない |
| 聞き手 | 質問なしで先へ進む。失敗はログと利用量の記録に残す | 質問は答えを良くするための補助で、なくても進められる。本人を止めない |
| 言い直し | エラーを返す。本人は再試行か「今すぐ担当者に送る」を選ぶ | 言い直しがないと確認ができない |
| 調査 | 進捗ストリームで失敗を伝える。段階は調査待ちのままで、再試行できる | 従来どおり |
| 説明 | 調査と照合の結果（技術メモ、出典、利用量）を保存したうえで、失敗を伝える。段階は調査待ちのまま | 費用をかけた調査の結果を失わない。この後「今すぐ担当者に送る」を使えば、担当者に調査の内容が届く |

説明が失敗した後に再試行した場合は、調査からやり直す。調査の結果を使い回す仕組みは、実際のモデルをつなぐ段階で費用を見て判断する。

## モックの構成

モックもスキルごとに別のクラスにする。発話のキーワードとタグの解釈は共通の補助クラスにまとめる。タグの一覧は `docs/api-contract.md` の「モックのシナリオ」が正。

## スキルごとの実装の切り替え

どのスキルをどの実装で動かすかは、スキルごとの設定で決める。全体をまとめて切り替える設定は持たない。

```yaml
inquiry:
  skills:
    reception:    { provider: mock }     # mock | ollama
    interviewer:  { provider: mock }
    restater:     { provider: mock }
    investigator: { provider: mock }
    explainer:    { provider: mock }
  knowledge:
    provider: mock                        # 一次情報の検索。いまは mock だけ
```

- 既定はすべて `mock`。設定を書かなければ、これまでどおり外部のAIに接続しない。
- 「モックで動いているか」は、Spring のプロファイルではなくこの設定から判断する。1つでも `mock` があれば「モックを含む」として扱う。
  - `GET /api/config` の `mock` は、1つでも `mock` があれば `true`。あわせて `skills`（スキルの識別子から実装名への対応）を返す。
  - 問い合わせ記録の `mock` は、その問い合わせで呼んだスキルのうち1つでもモックなら `true`。一部でもモックの結果が混ざった記録を、実際のモデルの記録として数えないため。
  - 本番（プロファイル `production`）では、スキルか一次情報の検索に1つでも `mock` があれば起動を止める。
- 調査だけモックにした場合、調査は問いの内容にかかわらずモックの決まった結果（求人の掲載期限についての事実）を返す。説明は、その事実をもとに実際のモデルが書く。問いと答えが噛み合わないことがあるが、これは調査がモックである間の制約。

手元のモデルで4つのスキルを動かす設定は、プロファイル `local-ai` にまとめる（`npm run dev:backend:local-ai`）。

## 手元のモデル（Ollama）で動かす実装

Bedrock の利用承認を待つ間、実際のモデルでスキルを試すための実装。問い合わせの内容もコードも外部に送らない。対象は受付、聞き手、言い直し、説明の4つ。調査は道具を繰り返し使うため、別の段階で扱う。

### 呼び出し方

`POST {base-url}/api/chat` を、ストリーミングなしで呼ぶ。HTTP は JDK 標準のクライアントを使い、ライブラリを足さない。

| 設定（スキルごと） | 意味 | `local-ai` での値 |
| --- | --- | --- |
| `model` | モデルの名前 | `qwen3.6:35b` |
| `temperature` | 出力のばらつき。0 で毎回同じ出力になる | すべて `0` |
| `think` | 考える過程を出力させるか。質は上がるが、応答が数十倍遅くなる | 説明だけ `true` |
| `timeout` | 1回の呼び出しの時間切れ | 受付・聞き手・言い直しは `60s`、説明は `120s` |

共通の設定は `inquiry.ollama.base-url`（既定 `http://localhost:11434`）と `inquiry.ollama.keep-alive`（モデルをメモリに残す時間。既定 `30m`）。

実測（Apple M5 Pro、64GB）: 考える過程なしで受付 0.3秒、聞き手 1秒、言い直し 1〜2秒、説明 0.5秒。考える過程ありで説明 16〜21秒、言い直し 20〜36秒。説明は調査の進捗表示の中で動くため、遅くても体験を損なわない。言い直しは本人の確認の場面なので、考える過程なしで使う。

`temperature` は必ず指定する。このモデルの既定値は 1 で、同じ入力でも出力が大きく揺れる（同じ訂正の試行が、5回中0回から4回まで変わった）。評価で結果を比べるには、出力が再現することが要る。

### 出力の形

**API の `format`（出力の形を JSON スキーマで縛る機能）は使わない。** 対象のモデルの版では未対応で、指定すると 501（`structured output is unavailable`）が返る。代わりに、プロンプトで「この形の JSON だけを出力する」と指示し、受け取った側で確かめる。指示だけで、試した範囲ではすべて正しい形の JSON が返った。

受け取った出力は次の順で扱う。

1. そのまま JSON として読む。
2. 読めなければ、最初の `{` から最後の `}` までを取り出して読む（コードブロックの記号や前置きがついた場合のため。考える過程ありのときに起きる）。
3. 読めた JSON を型に入れる。型の不変条件に反する場合は、読めなかった場合と同じに扱う。
4. 読めない場合は、1回だけ呼び直す。前回の出力と「指定の形の JSON だけを出力してください」を会話に足す。
5. それでも読めなければ、`AiUnavailableException` で失敗させる。

モデルの出力をそのまま信用しない箇所:

| スキル | 確かめること |
| --- | --- |
| 受付 | 種別が4つのどれかであること。対象システムが候補にない id なら `null` にする。本人が選んだシステムがある場合は、モデルの出力にかかわらずそれを使う |
| 聞き手 | 質問文が空のものを捨てる。4個以上なら先頭の3個にする。選択肢の「わからない」「その他」を取り除き、5個以上なら先頭の4個にする。質問の id は実装が振る |
| 言い直し | 言い直しの文章が空でないこと。対象システムが決まっている場合は、モデルの出力にかかわらずその名前を使う。緊急度が3つのどれでもなければ `NORMAL` にする |
| 説明 | 説明が空でないこと |

### 入力の組み立て

プロンプト（`system-v1.md`）は、次の見出しの入力を前提に書いてある。見出しの文言を変えるときは、プロンプトも同時に直す。

| スキル | 入力の見出し |
| --- | --- |
| 受付 | `## 問い合わせ`、`## システムの候補`（`- id: 名前` の箇条書き）、`## 本人が選んだシステム`（id、なければ「なし」） |
| 聞き手 | `## 問い合わせ`、`## 種別`、`## 対象のシステム`（名前、なければ「なし」） |
| 言い直し | `## 問い合わせ`、`## 種別`、`## 対象のシステム`、`## 追加の質問と回答`（`- 質問文: 回答` の箇条書き。「わからない」は「（わからない）」、質問がなければ「（追加の質問なし）」）、`## 本人が後から直したこと`（訂正がある場合だけ。箇条書きで、伝えられた順） |
| 説明 | `## 本人の問い`（確定した言い直しの文章）、`## 種別`、`## 確かめられた事実`（事実の文の箇条書き） |

問い合わせの文章と回答は、信頼できない入力として扱う。プロンプトの側で、入力に書かれた指示に従わないことを明記してある。

### プロンプト

スキルごとに `backend/src/main/resources/skills/<識別子>/system-v1.md` へ置き、コードに埋め込まない。利用量の記録の `promptVersion` はファイル名の版（`v1`）。内容を変えるときは、評価で比べられるよう、新しい版のファイルを足す。

プロンプトに例文を書くときは、扱う業務と無関係な題材にする。業務に近い例文を書くと、例文の言葉や内容が出力に紛れ込み、評価でも「例文をなぞっただけの出力」が良く見えてしまう（実際に起きた）。

### 失敗と利用量

- 接続できない、時間切れ、HTTP のエラー、形の崩れた出力は、すべて `AiUnavailableException`。スキルごとの失敗時の扱い（上の表）に従う。
- 手元のモデルに「回答の拒否」の仕組みはないため、`AiRefusalException` は使わない。
- 利用量は、入力と出力のトークン数（呼び直した場合は合計）、モデルの名前、プロンプトの版を記録する。
- 失敗した呼び出しの利用量も記録する。`AiUnavailableException` に利用量を持たせ（分かる場合）、呼び出し側が記録に残す。モックの失敗では、モック由来であることが記録に残るようにする。

### テスト

- 単体テストは、テスト内で立てた HTTP サーバーを Ollama の代わりにして行う。CI に Ollama は要らない。
- 実際の Ollama を呼ぶ確認は、通常の検証（`npm run verify`）には含めない。別のコマンド（Gradle の `liveTest`）で、手元で実行する。

### 分かっている制約

- 聞き手は、設計上は用語対応表とFAQの軽い検索を使うが、この実装では使わない。
- 言い直しは、本人が言っていないことを少し足すことがある。説明は、考える過程なしでは「確認できなかった」と書かずに事実だけを並べることがある。どちらも評価の仕組みで測って直す。
- スキルの品質の判断は、評価セットができるまで保留する。少ない回数を目で見た印象は、当てにならなかった。

## Bedrock をつなぐときの決まり

- スキルごとにモデルと effort を設定で持つ。
- プロンプトの置き場所と版の扱いは、手元のモデルと同じ。
- 出力の形は、API の構造化出力で縛る。手元のモデル用の「JSON を取り出して読む」処理は使わない。
- 評価セットはスキルごとに持ち、品質の基準に対応する指標で採点する。手元のモデルと同じ評価セットを使い、結果を比べる。
