# スキルの構成

AIに任せる仕事を8つのスキルに分け、呼ぶ順序と、機械的に確かめられること（根拠の照合、案の確認など）は通常のコードが担う。図と考え方は公開ページ（`site/index.html`）にある。この文書は実装の仕様を定める。

スキルは、本人向けの5つ（受付、聞き手、言い直し、調査、説明）と、担当者向けの3つ（助言、下書き、訳）。この文書は、作った順に書き足している。前半（「スキルの一覧」から「調査の実装」まで）は本人向けの5つを最初に作ったときの記述で、後ろの節（「入口の作り替えに伴う変更」「言語」「説明が出す手順」「担当者を支える2つのスキル」「助言と先例」「訳のスキル」）が新しい。食い違う箇所は、後ろの節を正とする。

## 分ける基準

スキルは、次のどれかが違う単位で分ける。どれも変わらない分割はしない。

- **品質の基準**: 何をもって良い出力とするか
- **使える道具**: 一次情報の検索を使うか、どこまで使うか
- **失敗のしかた**: 失敗したときに本人と担当者に何が起きるか

## スキルの一覧

インターフェースは `dev.inquiryassist.core.skill` に置き、Spring にも HTTP にも依存させない。実装（モック、のちに実際のモデル）はスキルごとに別のクラスにする。

| スキル | 識別子 | 仕事 | 道具 |
| --- | --- | --- | --- |
| 受付 | `reception` | 種別を判定し、対象システムを推測する | なし |
| 聞き手 | `interviewer` | 足りない情報を、非エンジニアが答えられる質問にする | 用語対応表とFAQの軽い検索 |
| 言い直し | `restater` | 言い直しの文章と構造化データを作る。作り直しも担う | 用語対応表 |
| 調査 | `investigator` | 一次情報を調べ、根拠つきの事実を集める | 読み取り専用の検索とファイル読み取り（繰り返し使う） |
| 説明 | `explainer` | 確かめられた事実だけから、本人向けの説明を書く | 用語対応表 |

識別子は列挙型 `Skill` で持ち、利用量の記録（`usages[].step`）にこの値を使う。言い直しの作り直しは `restater` として記録する。

### インターフェース

```java
interface ReceptionSkill {
    AiResult<Reception> receive(String utterance, List<SystemOption> candidates, SystemOption selected);
}

interface InterviewerSkill {
    AiResult<Interview> ask(String utterance, InquiryCategory category, SystemOption system, AccessScope scope);
}

interface RestaterSkill {
    AiResult<StructuredInquiry> restate(
            String utterance,
            InquiryCategory category,
            List<AnsweredQuestion> answers,
            SystemOption system,
            List<String> corrections);
}

interface InvestigatorSkill {
    AiResult<Investigation> investigate(StructuredInquiry inquiry, AccessScope scope, ProgressListener progress);
}

interface ExplainerSkill {
    AiResult<Explanation> explain(StructuredInquiry inquiry, List<Finding> confirmedFindings);
}
```

言い直しの作り直しは、別のメソッドにしない。本人が伝えた違う点（`corrections`。伝えられた順）を足して、最初から言い直す。前回の言い直しの文章は渡さない。前回の文章を渡すと、直すべき記述がそこに残っているため、訂正と食い違う文になりやすい（実際のモデルで確認した）。`corrections` が空なら最初の言い直し。

## 受け渡す型

| 型 | 中身 | 不変条件 |
| --- | --- | --- |
| `Reception` | `category`、`guessedSystemId`（任意） | `category` は必須 |
| `Interview` | `questions` | 最大3個 |
| `Finding` | `statement`（事実の一文）、`evidence`（その事実の根拠となる出典） | `evidence` は1件以上。根拠を挙げられない内容は事実にせず、「見つからなかったこと」か「次に確認すること」に入れる |
| `Investigation` | `findings`、`notFound`、`nextChecks` | — |
| `VerifiedInvestigation` | `confirmed`、`unconfirmed`、`notFound`、`nextChecks`、出典ごとの照合結果 | `confirmed` の各事実の `evidence` は照合を通った出典だけ |
| `Explanation` | `text`（本人向けの説明）、`answersQuestion`（確かめられた事実が本人の問いに答えているか）、`steps`（本人が自分で行える手順。なくてもよい。下の「説明が出す手順」） | `text` は空でない。`steps` は10個まで |

`Finding` が事実と根拠を対にして持つことが、この構成の要になる。事実と出典を別々の一覧で持つと、ある出典が照合で落ちたときに、どの事実が根拠を失ったのかが分からない。対にしておけば、根拠を失った事実だけを機械的に外せる。

## 調査から説明までの順序

調査、照合、説明の順に進める。この部分は `core` の `AnswerPipeline` にまとめ、Spring なしでテストできるようにする。

1. **調査**（AI）: `Investigation` を返す。進捗は調査のスキルが通知する。
2. **照合**（コード）: 出典ごとに実在を確かめ、事実を2つに分ける。
   - 根拠が1件でも照合を通った事実は `confirmed`。`evidence` は通った出典だけに絞る。
   - 根拠がすべて落ちた事実は `unconfirmed`。
3. **説明**（AI）: `confirmed` が1件以上あるときだけ呼ぶ。渡すのは `confirmed` だけで、`unconfirmed` は渡さない。説明のスキルは、確かめられなかった内容を知る手段を持たない。

進捗には、調査の通知に続けて「根拠を確かめています」と、説明を呼ぶ場合は「答えをまとめています」を加える。

結果は次のように組み立てる。

| 項目 | 中身 |
| --- | --- |
| `grounded` | `confirmed` が1件以上あるか |
| `answered` | `grounded` で、かつ説明のスキルが「問いに答えている」と判定したか。確かめられたが的外れな事実しか集まらなかった場合に、それを答えとして見せないために持つ。この判定は機械的に確かめられないため、モデルの判定に頼る。ただし判定が効くのは「答えとして見せない」方向だけで、誤って `true` になっても従来と同じ表示になるだけで済む |
| `askerExplanation` | 説明のスキルの出力。`grounded` でなければ `null` |
| `citations`（本人向け） | `confirmed` の事実の根拠（照合を通ったもの） |
| `memo.findings` | `confirmed` の事実の文 |
| `memo.unconfirmed` | `unconfirmed` の事実の文。担当者にだけ「根拠を確かめられなかったこと」として示す |
| `memo.notFound`、`memo.nextChecks` | 調査の出力のまま |

確かめられなかった事実を捨てずに `memo.unconfirmed` に残すのは、担当者にとっては調べる手がかりになるため。ただし事実としては示さず、必ず区別して表示する。

問い合わせた本人には見せない。本人は裏づけのない内容の真偽を判断できず、もっともらしい文面であればそのまま試してしまう。本人向けの応答には API の時点で含めず、画面での非表示には頼らない。

## 呼ぶ順序と種別

| 種別 | 受付 | 聞き手 | 言い直し | 調査・照合・説明 |
| --- | --- | --- | --- | --- |
| 仕様確認・相談 | 呼ぶ | 呼ぶ | 呼ぶ | 呼ぶ |
| 不具合の疑い | 呼ぶ | 呼ぶ | 呼ぶ | 呼ぶ |
| 作業依頼 | 呼ぶ | 呼ばない（固定の3問） | 呼ぶ | 呼ばない |
| 障害 | 呼ぶ | 呼ばない（固定の1問） | 「いいえ」で続行する場合だけ呼ぶ | 続行する場合だけ呼ぶ |

本人が種別を仕様確認・相談か不具合の疑いに変更し、聞き手の質問がまだない場合は、その時点で聞き手を呼ぶ。対象システムを変更しただけでは呼び直さない。

## 失敗したときの扱い

スキルごとに、失敗が本人に与える影響を変える。

| 失敗したスキル | 扱い | 理由 |
| --- | --- | --- |
| 受付 | 問い合わせを保存し、エラーと `inquiryId` を返す。本人は「今すぐ担当者に送る」を使える | 種別が分からないと先へ進めない |
| 聞き手 | 質問なしで先へ進む。失敗はログと利用量の記録に残す | 質問は答えを良くするための補助で、なくても進められる。本人を止めない |
| 言い直し | エラーを返す。本人は再試行か「今すぐ担当者に送る」を選ぶ | 言い直しがないと確認ができない |
| 調査 | 進捗ストリームで失敗を伝える。段階は調査待ちのままで、再試行できる | 従来どおり |
| 説明 | 調査と照合の結果（技術メモ、出典、利用量）を保存したうえで、失敗を伝える。段階は調査待ちのまま | 費用をかけた調査の結果を失わない。この後「今すぐ担当者に送る」を使えば、担当者に調査の内容が届く |

調査（調査、照合、説明の一続き）を呼ぶ場所は、本人が待っている間だけではない。担当者に渡した後にも、裏で呼ぶ（答えを待たずに送った件、業務が止まっている件、時間切れになった件）。呼ぶ場所は増えるが、`AnswerPipeline` を実行して結果を保存する役は1か所にまとめ、結果を誰に見せるかは、終わった時点の問い合わせの状態で決める（`api-contract.md` の「調査の状況と、裏での調査」）。スキルの側は、裏で呼ばれたかどうかを知らない。

- 本人が待つ調査が時間切れ（既定60秒）になったら、打ち切らずに担当者へ引き継ぎ、調査は裏で続ける。本人には、失敗ではなく引き継ぎとして伝える。
- 裏での調査の失敗は、本人には見せない。担当者に、失敗したことだけを示す。

説明が失敗した後に再試行した場合は、調査からやり直す。調査の結果を使い回す仕組みは、実際のモデルをつなぐ段階で費用を見て判断する。

## モックの構成

モックもスキルごとに別のクラスにする。発話のキーワードとタグの解釈は共通の補助クラスにまとめる。タグの一覧は `docs/api-contract.md` の「モックのシナリオ」が正。

## スキルごとの実装の切り替え

どのスキルをどの実装で動かすかは、スキルごとの設定で決める。全体をまとめて切り替える設定は持たない。

```yaml
inquiry:
  skills:
    reception:    { provider: mock }     # mock | ollama
    interviewer:  { provider: mock }
    restater:     { provider: mock }
    investigator: { provider: mock }
    explainer:    { provider: mock }
  knowledge:
    provider: mock                        # 一次情報の検索。いまは mock だけ
```

- 既定はすべて `mock`。設定を書かなければ、これまでどおり外部のAIに接続しない。
- 「モックで動いているか」は、Spring のプロファイルではなくこの設定から判断する。1つでも `mock` があれば「モックを含む」として扱う。
  - `GET /api/config` の `mock` は、1つでも `mock` があれば `true`。あわせて `skills`（スキルの識別子から実装名への対応）を返す。
  - 問い合わせ記録の `mock` は、その問い合わせで呼んだスキルのうち1つでもモックなら `true`。一部でもモックの結果が混ざった記録を、実際のモデルの記録として数えないため。
  - 本番（プロファイル `production`）では、スキルか一次情報の検索に1つでも `mock` があれば起動を止める。
- 調査だけモックにした場合、調査は問いの内容にかかわらずモックの決まった結果（求人の掲載期限についての事実）を返す。説明は、その事実をもとに実際のモデルが書く。問いと答えが噛み合わないことがあるが、これは調査がモックである間の制約。
- 調査を実際のモデルにし、一次情報の検索をモックにした場合、調査は見本の資料（`backend/src/main/resources/mock-knowledge/`）を実際に検索して読む。問いに応じた答えが返るが、調べられるのは見本の資料に書かれていることだけ。

手元のモデルで5つのスキルを動かす設定は、プロファイル `local-ai` にまとめる（`npm run dev:backend:local-ai`）。一次情報の検索はモックのまま。

## 手元のモデル（Ollama）で動かす実装

Bedrock の利用承認を待つ間、実際のモデルでスキルを試すための実装。問い合わせの内容もコードも外部に送らない。受付、聞き手、言い直し、説明の4つは、1回の呼び出しで JSON を受け取る（この節）。調査は道具を繰り返し使うため、呼び出し方が違う（次の節「調査の実装」）。

### 呼び出し方

`POST {base-url}/api/chat` を、ストリーミングなしで呼ぶ。HTTP は JDK 標準のクライアントを使い、ライブラリを足さない。

| 設定（スキルごと） | 意味 | `local-ai` での値 |
| --- | --- | --- |
| `model` | モデルの名前 | `qwen3.6:35b` |
| `temperature` | 出力のばらつき。0 で最も小さくなる | すべて `0` |
| `think` | 考える過程を出力させるか。質は上がるが、応答が数十倍遅くなる | 説明だけ `true` |
| `timeout` | 1回の呼び出しの時間切れ | 受付・聞き手・言い直しは `60s`、説明は `120s` |

共通の設定は `inquiry.ollama.base-url`（既定 `http://localhost:11434`）、`inquiry.ollama.keep-alive`（モデルをメモリに残す時間。既定 `30m`）、`inquiry.ollama.seed`（乱数の種。既定 `42`。`options.seed` として必ず送る）。

実測（Apple M5 Pro、64GB）: 考える過程なしで受付 0.3秒、聞き手 1秒、言い直し 1〜2秒、説明 0.5秒。考える過程ありで説明 16〜21秒、言い直し 20〜36秒。説明は調査の進捗表示の中で動くため、遅くても体験を損なわない。言い直しは本人の確認の場面なので、考える過程なしで使う。

`temperature` と `seed` は必ず指定する。このモデルの `temperature` の既定値は 1 で、同じ入力でも出力が大きく揺れる（同じ訂正の試行が、5回中0回から4回まで変わった）。

`temperature` を 0 にしても、出力は完全には再現しない。同じ条件で評価を2回実行すると、32件中14件で文面が変わり、1件は合否が入れ替わった。同じ入力を続けて呼ぶと揃うが、別の入力を間に挟むと揃わないことがある。`seed` を固定すると揃いやすくなるが、保証はない。評価では揺れを前提にし、繰り返して通った割合で比べる（`docs/evaluation.md`）。

### 出力の形

**API の `format`（出力の形を JSON スキーマで縛る機能）は使わない。** 対象のモデルの版では未対応で、指定すると 501（`structured output is unavailable`）が返る。代わりに、プロンプトで「この形の JSON だけを出力する」と指示し、受け取った側で確かめる。指示だけで、試した範囲ではすべて正しい形の JSON が返った。

受け取った出力は次の順で扱う。

1. そのまま JSON として読む。
2. 読めなければ、最初の `{` から最後の `}` までを取り出して読む（コードブロックの記号や前置きがついた場合のため。考える過程ありのときに起きる）。
3. 読めた JSON を型に入れる。型の不変条件に反する場合は、読めなかった場合と同じに扱う。
4. 読めない場合は、1回だけ呼び直す。前回の出力と「指定の形の JSON だけを出力してください」を会話に足す。
5. それでも読めなければ、`AiUnavailableException` で失敗させる。

モデルの出力をそのまま信用しない箇所:

| スキル | 確かめること |
| --- | --- |
| 受付 | 種別が4つのどれかであること。対象システムが候補にない id なら `null` にする。本人が選んだシステムがある場合は、モデルの出力にかかわらずそれを使う |
| 聞き手 | 質問文が空のものを捨てる。4個以上なら先頭の3個にする。選択肢の「わからない」「その他」を取り除き、5個以上なら先頭の4個にする。質問の id は実装が振る |
| 言い直し | 言い直しの文章が空でないこと。対象システムが決まっている場合は、モデルの出力にかかわらずその名前を使う。緊急度が3つのどれでもなければ `NORMAL` にする |
| 説明 | 説明が空でないこと |

### 入力の組み立て

プロンプト（`system-v1.md`）は、次の見出しの入力を前提に書いてある。見出しの文言を変えるときは、プロンプトも同時に直す。

| スキル | 入力の見出し |
| --- | --- |
| 受付 | `## 問い合わせ`、`## システムの候補`（`- id: 名前` の箇条書き）、`## 本人が選んだシステム`（id、なければ「なし」） |
| 聞き手 | `## 問い合わせ`、`## 種別`、`## 対象のシステム`（名前、なければ「なし」） |
| 言い直し | `## 問い合わせ`、`## 種別`、`## 対象のシステム`、`## 追加の質問と回答`（`- 質問文: 回答` の箇条書き。「わからない」は「（わからない）」、質問がなければ「（追加の質問なし）」）、`## 本人が後から直したこと`（訂正がある場合だけ。箇条書きで、伝えられた順） |
| 説明 | `## 本人の問い`（確定した言い直しの文章）、`## 種別`、`## 確かめられた事実`（事実の文の箇条書き） |

問い合わせの文章と回答は、信頼できない入力として扱う。プロンプトの側で、入力に書かれた指示に従わないことを明記してある。

### プロンプト

スキルごとに `backend/src/main/resources/skills/<識別子>/system-v1.md` へ置き、コードに埋め込まない。利用量の記録の `promptVersion` はファイル名の版（`v1`）。内容を変えるときは、評価で比べられるよう、新しい版のファイルを足す。

プロンプトに例文を書くときは、扱う業務と無関係な題材にする。業務に近い例文を書くと、例文の言葉や内容が出力に紛れ込み、評価でも「例文をなぞっただけの出力」が良く見えてしまう（実際に起きた）。

### 失敗と利用量

- 接続できない、時間切れ、HTTP のエラー、形の崩れた出力は、すべて `AiUnavailableException`。スキルごとの失敗時の扱い（上の表）に従う。
- 手元のモデルに「回答の拒否」の仕組みはないため、`AiRefusalException` は使わない。
- 利用量は、入力と出力のトークン数（呼び直した場合は合計）、モデルの名前、プロンプトの版を記録する。
- 失敗した呼び出しの利用量も記録する。`AiUnavailableException` に利用量を持たせ（分かる場合）、呼び出し側が記録に残す。モックの失敗では、モック由来であることが記録に残るようにする。

### テスト

- 単体テストは、テスト内で立てた HTTP サーバーを Ollama の代わりにして行う。CI に Ollama は要らない。
- 実際の Ollama を呼ぶ確認は、通常の検証（`npm run verify`）には含めない。別のコマンド（Gradle の `liveTest`）で、手元で実行する。

### 分かっている制約

- 聞き手は、設計上は用語対応表とFAQの軽い検索を使うが、この実装では使わない。
- 言い直しは、本人が言っていないことを少し足すことがある。説明は、考える過程なしでは「確認できなかった」と書かずに事実だけを並べることがある。どちらも評価の仕組みで測って直す。
- スキルの品質の判断は、評価セットができるまで保留する。少ない回数を目で見た印象は、当てにならなかった。

## 調査の実装（道具の繰り返し）

調査は、モデルに道具を渡し、モデルが道具を呼ばずに結果を出力するまで呼び出しを繰り返す。Ollama の `POST /api/chat` に `tools` を添える（対象のモデルは道具の呼び出しに対応している）。

### 道具

道具は2つで、どちらも読み取り専用。`KnowledgeSearch` を通るため、閲覧範囲はそこで適用される。書き込む道具、外部に送る道具は持たせない。

| 道具 | 引数 | 返すもの |
| --- | --- | --- |
| `search` | `query`（検索する語） | 該当した行（種類、資料の集まりの名前、パス、行番号、本文）。12件まで |
| `read` | `repository`、`path`、`startLine`、`endLine` | 行番号つきの本文。1回に120行まで |

道具の失敗（存在しないファイル、範囲外の行、閲覧できない資料、引数の不足、知らない名前の道具）は、調査を失敗させず、道具の結果として `{"error": "..."}` を返す。モデルが別の調べ方に切り替えられるようにするため。

### モデルに任せず、コードで決めること

| 決まり | 値 | 理由 |
| --- | --- | --- |
| 道具を渡して呼ぶ回数の上限 | 8回 | 終わらない調査を止める。超えたら、道具を渡さずに「ここまでに分かったことだけで出力する」よう求める |
| 1回の応答で実行する道具の数 | 4つ | 超えた分は実行せず、その旨を返す |
| 返す事実の数 | 5件 | 先頭の5件にする |
| 行番号 | モデルに書かせない | モデルの書く行番号はずれる。モデルには引用（資料からそのまま写した一節）だけを書かせ、行番号は調査の間に道具で実際に見た行から求める（`EvidenceLocator`） |
| 引用の最小の長さ | 空白を除いて6文字 | 短い引用はどこにでも当たるため、根拠にしない |
| 資料を調べずに出した結果 | 受け取らない | 1度だけ「まず search で調べる」よう求める。それでも調べなければ、事実をすべて捨てる。実際に、調べずに架空のファイルを根拠にした事実を返したことがあった |
| 根拠のない事実 | 捨てる | 根拠を1件も作れない事実（根拠の欄が空、引用が短すぎる）は、事実にしない |

見た行の中に引用が見つからない場合も、出典は作る（行は1行目を指す）。その出典は照合（`CitationVerifier`）で落ち、事実は「根拠を確かめられなかったこと」として担当者にだけ見える。調査の実装は合否を決めず、確かめる役は照合に一本化する。

### 出力と入力

結果は、道具を呼ばない応答の本文として、次の形の JSON で受け取る。読み方と、読めなかったときの扱い（1回だけ求め直す、2回目は `UnreadableOutputException`）は、ほかのスキルと同じ。

```json
{"findings": [{"statement": "事実の1文", "evidence": [{"repository": "...", "path": "...", "quote": "資料からそのまま写した一節"}]}],
 "notFound": ["調べたが見つからなかったこと"], "nextChecks": ["担当者が確認すべきこと"]}
```

入力の見出しは `## 本人の問い`（確定した言い直しの文章）、`## 種別`、`## 対象のシステム`（名前、なければ「なし」）、`## 起きていること`、`## 期待していた結果`（後ろの2つは、ある場合だけ）。

問いの文章に加えて、資料の本文も信頼できない入力として扱う。資料に指示のような文章が書かれていても従わないことを、プロンプトに明記してある。道具が読み取り専用なので、従ってしまった場合の影響は「誤った事実を返す」までに留まり、その事実も引用の照合を通らなければ本人には見えない。

### 進捗

進捗は、道具を実行するたびに通知する。文言は固定で、モデルが選んだ検索の語やファイルの名前は出さない（内部の言葉が画面に出るのを避ける）。検索は「資料を検索しています」、読み取りは資料の種類に応じて「コードを読んでいます」「FAQを読んでいます」「用語対応表を確認しています」「資料を読んでいます」。同じ文言は続けて通知しない。

### 設定と実測

`local-ai` では、考える過程なし、1回の呼び出しの時間切れ 120秒。利用量は、すべての呼び出しの合計を記録する。途中で失敗した場合も、そこまでの合計を記録する。

実測（見本の資料、4つの問い）: 1.5〜4秒、呼び出しは2〜5回、入力は1,200〜9,200トークン。入力は、道具の結果が会話に積み重なるため、呼び出しの回数とともに増える。

### 分かっている制約

- 見本の資料の検索（`MockKnowledgeSearch`）は、空白で区切った語のどれかを含む行を返すだけ。語を増やすほど関係のない行が増える。実際のリポジトリを調べる検索は未実装。
- 引用が資料に実在することは確かめるが、その引用が事実の文を裏づけているかは確かめていない。説明のスキルの `answered` の判定が、問いと事実の食い違いを一部拾う。
- 調査の品質は、評価の例をまだ作っておらず、測っていない。

## 入口の作り替えに伴う変更

入口を、選択肢を押していく一問一答に変えた（`api-contract.md` の「入口の質問」）。これに伴い、3つのスキルの役割と受け渡しが変わる。この節が、上の記述より新しい。食い違う箇所は、この節を正とする。

### 種類と緊急度

- 種別（`InquiryCategory`、4つ）を、種類（`InquiryType`、5つ）に置き換える: `HOW_TO`、`HOW_IT_WORKS`、`LOOKS_WRONG`、`DO_FOR_ME`、`CHANGE_REQUEST`。障害は種類から外し、問い合わせの緊急度（`NORMAL`、`HURRY`、`BLOCKED`）として持つ。
- 種類ごとの経路（調べるか、答えの後にどうなるか）は、`InquiryType` に集約する。経路は `api-contract.md` の「種類ごとの経路」の表。
- 言い直しの出力から `urgency` を外す。緊急度は本人が申告するもので、AI が文章から決めるものではない（文面から補うのは、後の版）。

### スキルごとの変更

| スキル | いつ呼ぶか | 入力 | 出力 |
| --- | --- | --- | --- |
| 受付 | 本人が文章を書いたときだけ（最初から文章で始めた、途中で切り替えた）。押して答えただけなら呼ばない | 文章、システムと機能の候補、本人が既に選んだ置き場所 | まだ決まっていない置き場所（種類、システム、機能）。読み取れないものは null |
| 聞き手（質問を作る） | 置き場所の質問が終わり、マスの設定に詳しい質問がないとき | 種類、システム、機能、本人が書いた文章（なければ、ない旨） | 質問（0〜2個） |
| 聞き手（答えを読み取る） | マスの設定に詳しい質問があり、本人が文章を書いているとき | 本人が書いた文章、設定の質問（id、質問文、選択肢） | 文章に答えが書かれている質問の、id と答え |
| 言い直し | 入口の質問を終えたとき、作り直すとき | 置き場所（種類、システム、機能）、詳しい質問と答え、本人が書いた文章、本人が後から直したこと | 組み立てた問い（`summary`、`targetSystem`、`goal`、`whatHappened`、`expectedResult`） |
| 調査、説明 | 変更なし。種別の代わりに種類を受け取る | — | — |

- 受付は、本人が既に選んだ置き場所を変えない。モデルの出力にかかわらず、選んだ値を使う。候補にない id は null にする。機能は、決まったシステムの機能でなければ null にする。
- 聞き手の2つの仕事は、「足りない情報だけを本人に聞く」という同じ役割の2つの面なので、1つのスキルにまとめる。品質の基準（聞かなくてよいことを聞かない）も、失敗のしかた（失敗しても先へ進める）も同じ。指示文と出力の形は違うため、指示文のファイルは分ける（`skills/interviewer/prefill-v1.md`）。
- 答えの読み取りは、出力を信用しない。選択肢は、その質問の選択肢にあるものだけを採る。文章で答える質問は、返された答えが本人の文章の中にそのまま含まれている場合だけ採る（空白の違いは無視する）。この確かめは、聞き手の実装ではなく、入口の処理（`core/intake`）が行う。モックでも実際のモデルでも同じ確かめを通すため。
- 受付が失敗しても、エラーにしない。置き場所は置かれず、質問として聞く。押して答える入口は、AI なしでも最後の質問まで進める。
- 言い直しは、読み取れた目的を文章に含める（「〜したいので、〜を知りたい」）。読み取れなければ、作らない。
- 種類が決まっていない（本人が「わからない」と答え、受付も置けなかった）場合も、言い直しは呼ぶ。調査は、種類が決まっていない場合は `HOW_IT_WORKS` と同じ経路で行う。

### 入力の見出し（Ollama の実装）

指示文は v2（`system-v2.md`）。次の見出しの入力を前提に書いてある。

| スキル | 入力の見出し |
| --- | --- |
| 受付 | `## 文章`、`## システムの候補`（`- id: 名前` の箇条書き。機能は、システムの下に2文字の字下げで `  - id: 名前`）、`## 既に決まっていること`（`- 種類: HOW_TO`、`- システム: id`、`- 機能: id` の箇条書き。なければ「なし」） |
| 聞き手（質問を作る） | `## 種類`（決まっていなければ「（未定）」）、`## システム`、`## 機能`（どちらも名前。決まっていなければ「なし」）、`## 本人が書いた文章`（なければ「（なし）」） |
| 聞き手（答えを読み取る） | `## 本人が書いた文章`、`## 質問`（質問ごとに `- id: 質問文` の1行。選択肢のある質問は、その下に2文字の字下げで `  - 選択肢の id: 名前` を並べる。選択肢のない質問は、字下げで `  - （文章で答える）`） |
| 言い直し | `## 種類`、`## システム`、`## 機能`、`## 質問と答え`（`- 質問文: 答え` の箇条書き。「わからない」は「（わからない）」。なければ「（なし）」）、`## 本人が書いた文章`（なければ「（なし）」）、`## 本人が後から直したこと`（訂正がある場合だけ） |
| 説明 | `## 本人の問い`、`## 種類`、`## 確かめられた事実` |

受付の出力は `{"type": …, "systemId": …, "functionId": …}`。聞き手（答えを読み取る）の出力は `{"answers": [{"questionId": …, "optionId": … または null, "text": … または null}]}`。文章に答えが書かれていない質問は、`answers` に入れない。言い直しの出力から `urgency` はなくなる。受付、聞き手、言い直し、説明の v1 の指示文は、新しい種類では動かないため削除した。調査は v1 のまま。

## 言語

AI は、本人の言語（問い合わせの `language`。`api-contract.md` の「言語」の節）で書く。

- 呼ぶ側（`InquiryService` と `AnswerPipeline`）が、スキルに渡す入力に本人の言語を加える。スキルは、自分では言語を決めない。
- 人が読む文章を書くスキル（聞き手の質問づくり、言い直し、調査、説明）が、この言語で書く。受付と、聞き手の読み取りは、識別子だけを返すので言語に関わらない。
- スキルに渡す設定の名前（種類、システム、機能、質問、選択肢）は、本人の言語の名前。
- 根拠の引用は訳さない。照合（`InvestigationVerifier`）は、引用が資料に書かれたとおりかを確かめるため、訳した引用は照合で落ちる。

### 手元のモデル（Ollama）の実装

- 指示文（`system-v2.md` など）は日本語で書かれ、日本語で書くことを前提にしている。本人の言語が日本語のときは、指示文をそのまま使う。**日本語のときに送る内容は、言語に対応する前と1文字も変わらない。** このため、これまでの評価の結果はそのまま有効。
- 本人の言語が日本語でないときだけ、指示文の末尾に、書く言語の指示（`skills/shared/output-language-v1.md`）を足す。`{{language}}` は、言語の名前（`en` なら `英語（English）`）に置き換える。
- モデルに向けた内部の文章（道具の説明、調べ直しを求める文）は、日本語のまま。
- 調べている間の進捗の文言は、本人の言語で出す。

### 分かっている制約

- 日本語以外で書かせたときの品質は、評価していない（評価の例がない）。
- 資料は日本語で書かれている。英語の問いから日本語の資料を探せるかは、モデルが日本語の言葉で検索できるかに依存する。言語をまたいで調べることを確かなものにするのは、段階3（LG-6）。
- 本人の文章が、本人の言語（画面の言語）と違う言語で書かれていても、文章の言語は見ない。

## 説明が出す手順

「使い方を知りたい」と「やってほしい」では、本人が知りたいのは、何をどの順に行えばよいか。説明のスキルは、確かめられた事実から操作の順に並べられる場合に、文章の説明に加えて、手順（`steps`）を出す。

- 手順は、行う順に並べる。それぞれ `action`（何をするか。画面の名前、押す場所、入力する値をできるだけ具体的に）と、`check`（結果の確かめ方。なければ `null`）を持つ。
- 手順も、説明と同じく、確かめられた事実だけから書く。事実から手順を組めなければ、出さない（空のまま）。無理に作らない。
- 新しいスキルにはしない。品質の基準（確かめられた事実だけから、本人に向けて、業務の言葉で書く）も、道具も、失敗のしかたも、説明と同じため。出力の形が1つ増えるだけ。
- 問いに答えていない説明（`answersQuestion` が `false`）の手順は、コードが捨てる（答えの型 `ZeroAnswer` が、問いに答えていない答えに手順を持たせない）。答えになっていない手順を、本人が試さないようにするため。
- 担当者向けの手順の案（助言の `procedure`）とは別のもの。こちらは本人が自分で行う操作で、本人に見せる。助言の手順は担当者が行う作業で、担当者だけに見せる。
- 実装: モックの説明は、種類が `HOW_TO` か `DO_FOR_ME` のときに手順を返す。手元のモデル（Ollama）の説明は、手順を返さない（指示文と出力の形を変えていない。日本語のときモデルに送る内容を変えない決まりのため）。手元のモデルで手順を出すには、説明の指示文の新しい版を足し、評価で前の版と比べる。

## 担当者を支える2つのスキル（助言、下書き）

担当者に渡った件で、AI が担当者を支える。本人向けの5つのスキルに、担当者向けの2つを足す。この節が、上の「スキルの一覧」より新しい（スキルは7つになる。後ろの「訳のスキル」で、8つになる）。

| スキル | 識別子 | 仕事 | 道具 | 読み手 |
| --- | --- | --- | --- | --- |
| 助言 | `advisor` | 確かめられた事実から、判断の案（相談が要るかを含む）と、作業の手順の案を作る | なし（調査の結果を受け取る。自分では調べない） | 担当者 |
| 下書き | `drafter` | 担当者が本人に送る文章（聞き返し、結果）の下書きを作る | なし | 本人（担当者が確かめ、直してから送る） |

### 分ける理由

- **助言を、説明と分ける**: 読み手が違う（説明は本人に、業務の言葉で、事実だけを書く。助言は担当者に、技術の言葉で、事実から先の「案」を書く）。品質の基準が違う。失敗のしかたも違う（助言が失敗しても、誰も止まらない。担当者は案なしで進められる）。
- **下書きを、助言と分ける**: 読み手が違う（本人）。呼ぶ時点も違う（助言は材料が揃った時点で裏で作る。下書きは、担当者が頼んだときに、担当者が決めた方向に沿って作る）。
- **下書きを、説明と分ける**: 入力が違う（担当者の意図と、それまでのやり取りを受け取る）。説明は「確かめられた事実だけから書く」ことが品質の基準だが、下書きは担当者の判断を伝える文章で、事実にないこと（担当者が決めたこと）を含む。

### インターフェースと型

```java
interface AdvisorSkill {
    AiResult<Advice> advise(StructuredInquiry inquiry, InquiryType type, List<Finding> confirmedFindings, String language);
}

interface DrafterSkill {
    AiResult<Draft> draft(DraftRequest request);
}
```

| 型 | 中身 | 不変条件 |
| --- | --- | --- |
| `Advice` | `judgment`（判断の案。なくてもよい）、`procedure`（手順の案。なくてもよい） | — |
| `Advice.Judgment` | `text`（案の文章）、`needsConsultation`（仕様の持ち主への相談が要りそうか）、`consultationReason`（要る場合の理由）、`basedOn`（基づく事実の番号。渡した事実の並びの、1から始まる番号） | `text` は空でない |
| `Advice.Procedure` | `steps`（順に行う手順。それぞれ `target`（対象）、`action`（操作やコマンド）、`check`（結果の確かめ方））、`rollback`（元に戻す方法。なければ `null`）、`basedOn` | `steps` は1件以上 |
| `DraftRequest` | `kind`（`ASK` 聞き返し／`RESULT` 結果）、`inquiry`（言い直した問い）、`confirmedFindings`、`judgment`（判断の案の文章。あれば）、`messages`（それまでのやり取り）、`note`（担当者が伝えたいこと。任意）、`language`（本人の言語） | — |
| `Draft` | `text`（下書きの文章） | 空でない |

### 案は、事実に基づくものだけを出す（コードで確かめる）

助言の出力は、通常のコード（`core` の `AdviceVerifier`）で確かめてから保存する。機械的に確かめられることを、AI に任せない。

- `basedOn` のうち、渡した事実の番号として存在しないものは外す。
- 外した結果、`basedOn` が空になった案（判断の案、手順の案のそれぞれ）は捨てる。基づくものがない案は、出さない。
- 確かめられた事実が1つもない問い合わせでは、助言を呼ばない。

案が事実から正しく導かれているかは、機械的には確かめられない。そのため、担当者の画面では、案を事実と区別して示し、基づく事実を並べて見せる。決めるのは担当者。

### 呼ぶ時点

- **助言**: 担当者の番の問い合わせに、調査の結果（確かめられた事実が1つ以上）があり、その結果に対する案がまだないとき、裏で呼ぶ。きっかけは2つ: 調査の結果を保存した時点で担当者に渡っている（裏での調査が終わった、答えの完了と同時に担当者に渡った）、または、調査の結果を持つ問い合わせが担当者に渡った（本人が「解決していない」と答えた）。本人が待っている間は呼ばない（本人の待ち時間を延ばさない）。
- **下書き**: 担当者が頼んだときだけ（`api-contract.md` の「担当者の操作」）。結果は保存しない（担当者の入力欄に入るだけ。送られた文章は、担当者の発言として残る）。利用量は記録する。

### 言語

- 助言は、既定の言語で書く（読み手は担当者。担当者ごとの言語は、書く時点では分からない）。
- 下書きは、本人の言語で書く（送る相手は本人）。

### 失敗したときの扱い

| 失敗したスキル | 扱い | 理由 |
| --- | --- | --- |
| 助言 | 案なしで進める。担当者のパネルに、失敗したことだけを示す。本人には何も起きない | 案は補助で、なくても担当者は判断できる |
| 下書き | 担当者にエラーを返す。担当者は、自分で書く | 同上 |

### 実装

このリポジトリ（骨組み）では、2つともモックの実装だけを持つ（`inquiry.skills.advisor.provider`、`inquiry.skills.drafter.provider` は `mock` だけ。ほかの値を指定すると起動を止める）。手元のモデルの実装は作らない。プロファイル `local-ai` でも、この2つはモックで動く。本番では、モックを含む構成は起動できないので、実際のモデルの実装を足すまで本番には出せない。

## 助言と先例

助言は、確かめられた事実に加えて、同じ置き場所の先例（仕様の持ち主が下した決定の記録）を受け取る。先例が増えるほど、担当者が自分のところで終わらせられる件が増える。この節が、上の「担当者を支える2つのスキル」のインターフェースより新しい。

```java
interface AdvisorSkill {
    AiResult<Advice> advise(
            StructuredInquiry inquiry, InquiryType type, List<Finding> confirmedFindings,
            List<PrecedentNote> precedents, String language);
}
```

- `PrecedentNote` は、先例のうち助言に渡す部分（状況、決定の種類、決定の内容、理由）。決めた人の名前と、元の問い合わせは渡さない（案を作るのに要らない）。
- `Advice.Judgment` と `Advice.Procedure` は、`basedOn`（事実の番号）に加えて、`basedOnPrecedents`（先例の番号。渡した先例の並びの、1から始まる番号）を持つ。
- **コードで確かめること**（`AdviceVerifier`）: 事実の番号と先例の番号のそれぞれについて、存在しないものを外す。外した結果、どちらも空になった案は捨てる。
- **先例を探すのは、コード**。同じ置き場所（システムと種類が同じ）の先例を、機能が同じものを先にして、新しい順に5件まで引く。似ているかどうかの判断は、助言に任せる（渡された先例のうち、当てはまるものだけを案の根拠にする）。先例は言語を問わずに引き、書かれた言語のまま渡す。
- **呼ぶ条件**: 確かめられた事実が1つ以上、または同じ置き場所の先例が1つ以上。調べない種類（変えてほしい）の件でも、先例があれば案が出る。
- 下書きには、その問い合わせについての決定（あれば）を渡す（`DraftRequest.decision`）。担当者が伝える結果の中心は、決定の内容になるため。
- 先例は、人が下した決定なので溜める。AI の答えと案は溜めず、毎回作り直す。

## 訳のスキル

本人の言語と担当者の言語が違う場合に、担当者に訳を添える。担当者向けの3つ目のスキルとして足す（スキルは8つになる）。

| スキル | 識別子 | 仕事 | 道具 | 読み手 |
| --- | --- | --- | --- | --- |
| 訳 | `translator` | 本人の言語で書かれた文章を、担当者の言語に訳す | なし | 担当者 |

- **分ける理由**: 品質の基準が違う。訳は、原文の意味を変えない、足さない、省かないことが基準で、何かを判断したり、書き直したりしない。失敗のしかたも違う（失敗しても、原文は見えている）。
- **インターフェース**: `AiResult<Translation> translate(List<String> texts, String from, String to)`。`Translation` は `texts`（訳した文章。渡した順）を持つ。
- **コードで確かめること**: 返ってきた文章の数が、渡した数と同じであること。違えば、失敗として扱う（どの訳がどの原文のものか、分からなくなるため）。訳の中身が正しいかは、機械的には確かめられない。そのため、訳は必ず原文に添えて出し、原文を置き換えない。
- **呼ぶ時点**: 担当者が頼んだときだけ（`api-contract.md` の「担当者の操作」）。訳した文章は、保存しない。
- **訳さないもの**: 根拠の引用（資料の原文のまま示す決まり）。設定の名前と画面の文言（言語ごとに持っている）。担当者が書いた文章と、AI の案（担当者の言語の側にある）。
- **本人には見せない**: 訳は担当者のためのもの。本人のページには、書かれたときのままの文章だけを出す。
- **逆の向き**（担当者から本人へ）は、下書きのスキルが担う。担当者が「伝えたいこと」を自分の言語で書けば、下書きが本人の言語の文章にする。
- **失敗したときの扱い**: 担当者にエラーを返す。原文は、これまでどおり見えている。
- **実装**: モックだけ（`inquiry.skills.translator.provider` は `mock` だけ）。

## Bedrock をつなぐときの決まり

- スキルごとにモデルと effort を設定で持つ。
- プロンプトの置き場所と版の扱いは、手元のモデルと同じ。
- 出力の形は、API の構造化出力で縛る。手元のモデル用の「JSON を取り出して読む」処理は使わない。
- 評価セットはスキルごとに持ち、品質の基準に対応する指標で採点する。手元のモデルと同じ評価セットを使い、結果を比べる。
