## 1. 背景と目的

### 背景

開発チームには、社内のメンバーから問い合わせが届く。本人は状況を知っているが埋め方を知らず、開発チームは埋め方を知っているが状況を知らない。この食い違いを突き合わせる作業に、双方の時間がかかっている。

### 目的

問い合わせ対応にかかる4つの費用を下げる。

1. **伝える費用**: 状況を、相手に通じる問いに直す作業
2. **待つ費用**: 埋められる人の手が空くまで、本人が止まっている時間
3. **届け先を誤る費用**: 不足の種類と、それを埋められる人が噛み合わないこと
4. **繰り返す費用**: 同じ不足が、何度も問い合わせとして現れること

### 目指す状態

担当者が AI を使い切って、自分のところで完結させる。仕様の持ち主への相談は、新しい決定が要るときだけになる。

### 内製する理由

型は Jira Service Management（以下 JSM）と同じものを作る。それでも内製するのは、次の理由による。

1. 外部ツールの予算より、AI の予算のほうが確保しやすく、着手から利用までが短い
2. 社内のソースコードなどの機密を外部に渡さずに、AI に読ませられる
3. 取り回しがよく、担当者や関係者の改善の要望にすぐ応えられる

この3つは、要件の優先順位を決める基準でもある。2 は機能以外の要件（5章）の中心になり、3 は設定の要件（4.7）の根拠になる。

## 2. 利用者

| 役割 | 誰か | 主に使う画面 |
| --- | --- | --- |
| 本人 | 問い合わせる社内のメンバー。エンジニアとは限らない | 入力、送った問い合わせ |
| 担当者 | 開発チームのメンバー | 担当者のボード、詳細 |
| 仕様の持ち主 | 相談を受け、新しい決定を下す人 | 相談された件の詳細 |
| 設定する人 | システム、機能、担当、期限を保つ人 | 設定 |

役割であり、1人が複数を兼ねてよい。

次の版で、その件に加えられた人（本人の上長、同じ件で困っている同僚、不在時の代わりの人）が加わる。加えられた件だけを見られ、追記できる（OP-15）。

## 3. 範囲

### 作るもの

社内のメンバーから開発チームへの問い合わせについて、入口から終了、蓄積までを扱う（`framework.md` の5つの面と2つの土台）。

### 作らないもの

| 作らないもの | 理由 |
| --- | --- |
| 障害の連絡と対応 | 専用の経路が別にある。このツールは「業務が止まっている」件を、待たせずに担当者へ渡すところまで |
| 「変えてほしい」の採用後の開発の管理 | 問い合わせとしては、採否が決まって伝わった時点で終わる。実際に変える作業は開発の流れで管理する |
| 社外の顧客からの問い合わせ | 利用者は社内に限る |
| 機器やライセンスの台帳、変更の可否を審議する会議やリスクの評価、夜間や休日の呼び出し | JSM が持つ IT 運用の機能のうち、問い合わせ対応の4つの費用に効かない部分。資産、変更、当番は、費用に効く形に絞って作る（下の「形を変えて含めるもの」） |
| 自由な雑談のできるチャット | 文章を書く場面を、最初の入力と訂正の一言に絞る方針（`ux-principles.md`） |
| AI が自分で操作や作業を実行すること | AI は決めず、作業しない。ただし、手順はできるだけ具体的に示す（KN-7、KN-8、OP-12）。人が手順を確かめて承認したら AI が実行する形は、手順の提示が安定してから検討する。その根拠には、示した手順を担当者がそのまま実行できた割合を使う |

### 形を変えて含めるもの

IT 運用の3つの機能は、そのままの形では作らないが、4つの費用に効く形に絞って含める。

| 機能 | この要件定義での形 | 効く費用 | 要件 |
| --- | --- | --- | --- |
| 資産の管理 | **システムと機能の台帳。** 置き場所の軸そのもの。システムと機能ごとに、担当、相談先、資料の場所、関連するシステムを持つ | 届け先を誤る費用 | CF-1、CF-3 |
| 変更の管理 | **変更の記録。** いつ、どのシステムのどの機能で、何が変わったか。AI が調査の材料にし、入口のお知らせに出し、関係する問い合わせの本人に知らせる | 繰り返す費用、伝える費用 | 4.10 |
| 当番の管理 | **当番表。** マスの担当を、期間ごとの担当者として持つ | 待つ費用 | OP-10 |

### 最初の版の範囲

最初の版は、社内で使い始められる最小の形を指す。実装の順番（7章）の1〜3と、4のうち「返事がないまま期間が過ぎたら回答済みにする」処理（CL-7）を含める。

- **最初の版**: 置き場所と状態、担当者で完結させる流れ、相談と先例、期間で回答済みにする処理。ここまでで「担当者が AI を使って完結し、足りないときだけ相談する」流れが通る
- **次の版**: 残りの時間が起こす出来事（期限、入力途中の取り下げ、開き直せる期間）、測るもの、変更の記録

CL-7 だけを前倒しするのは、結果を本人が確かめると決めたため。返事のない件を期間で終える処理がないと、開いたままの件が溜まり続け、担当者のボードが使えなくなる。

実際に使い始めるには、これとは別に、社内の環境に合わせた土台（認証、実際の資料の検索、承認された環境のモデル）が要る。7章の「別」として分ける。

各要件の「版」の欄に、初（最初の版）、次（次の版）、後（それ以降）を示す。

## 4. 機能の要件

### 4.1 入口

入口は、選択肢を押していく一問一答を基本にする。書くより押すほうが、始める負担が軽い。押して得られた情報から AI が問いを組み立て、「つまり、こういうことですね」と本人に確かめる。文章で書きたい人、選択肢に当てはまらない人のために、文章で書く道を必ず残す。

| 番号 | 要件 | 版 | いま |
| --- | --- | --- | --- |
| IN-1 | 本人は、選択肢を押していく一問一答で、問い合わせを始められる。1度に出す質問は1つ。聞く順は、種類（何をしたいか）、システム、機能、マスごとの詳しい質問。選択肢は、本人の言葉で書く | 初 | 済 |
| IN-2 | どの質問でも「わからない」を選べる。選べなくても先へ進める | 初 | 済 |
| IN-3 | 本人は、緊急度（通常、急ぎ、業務が止まっている）を申告できる。申告しなければ通常 | 初 | 済 |
| IN-7 | どの時点でも「文章で書く」に切り替えられる。最初から文章で書いて始めることもできる。書いた内容から分かることは、質問を省く | 初 | 済 |
| IN-8 | 選んだ内容と書いた内容を、後の質問で聞き直さない | 初 | 済 |
| IN-9 | 質問に答え終えた後、補足を任意で書ける。書かなくても進める | 初 | 済 |
| IN-4 | ほかのツールから、文章を入力欄に入れた状態で入口を開ける（自動では送信しない） | 初 | 済 |
| IN-5 | フォーム以外の入口（Slack など）から問い合わせられる | 後 | 未 |
| IN-6 | 入口に、お知らせ（既に分かっている障害や変更）を出せる | 次 | 未 |

### 4.2 受付

| 番号 | 要件 | 版 | いま |
| --- | --- | --- | --- |
| RC-1 | 本人が選んだ種類、システム、機能で、問い合わせをマスに置く。本人が選ばなかった軸（「わからない」と答えた、または文章で書いた）だけ、AI が置く。本人が選んだものは変えない。置けない場合は「わからない」の列に置く | 初 | 済 |
| RC-2 | マスが決まった後、足りない情報を、本人が画面を見れば答えられる質問として、選択肢つきで1問ずつ聞く。マスに「毎回聞くこと」が設定されていればそれを使い、足りなければ AI が質問を作る。マスごとの詳しい質問は3つまで | 初 | 済 |
| RC-3 | AI が、選んだ内容と書いた内容から問いを組み立て、「つまり、こういうことですね」と文章で示す。読み取れた目的（何をしたくて尋ねているか）を文に含める。読み取れなければ、無理に書かない。本人が確かめる。違えば一言で直せ（2回まで）、自分で書き直すこともできる | 初 | 済（目的を読み取って文に含める品質は、評価していない） |
| RC-4 | 緊急度が「業務が止まっている」の件は、マスごとの詳しい質問を省き、すぐ担当者の番にする。置き場所の質問と、状況の一言は聞く。AI の調査は裏で行う | 初 | 済（詳しい質問を省いて、すぐ担当者の番になる。調査は渡した後に裏で行い、結果と案を担当者に渡す。案を作る実装はモックだけ） |
| RC-5 | 本人は、問いを確かめた後であれば、AI の答えを待たずに担当者へ送れる。それより前には送れない。省けるのは「AI の答えを読んで、自分で確かめる手順」だけで、入力（置き場所の質問、マスの必須の質問、問いの確認）は省けない | 初 | 済 |
| RC-8 | 本人が答えを待たずに送った場合も、AI の調査は裏で行い、材料と案を担当者に渡す | 初 | 済（調査は裏で行い、結果と案を担当者に渡す。案を作る実装はモックだけ） |
| RC-9 | 入力の質問は、どれも「わからない」で進められる。ただし、すべてに「わからない」と答えた場合は、状況を一言書いてもらう。手がかりが何もないまま担当者に渡さない | 初 | 済 |
| RC-6 | AI が失敗した場合は、その時点の内容で担当者に送れる。こちらの失敗を理由に、本人を止めない。問い合わせは必ず保存する | 初 | 済 |
| RC-7 | AI が文面から緊急度の申告を補う（本人が通常のまま「全員が使えない」と書いた場合など）。変えた場合は本人に示す | 次 | 未 |

### 4.3 対応: 分かる

| 番号 | 要件 | 版 | いま |
| --- | --- | --- | --- |
| KN-1 | AI が、資料（コード、FAQ、用語）を読み取り専用で調べ、事実と根拠を対で集める | 初 | 済（見本の資料） |
| KN-2 | 根拠の実在を機械的に照合する。本人に見せるのは、確かめられた事実から書いた説明だけ。確かめられなかった内容は、担当者にだけ渡す | 初 | 済 |
| KN-3 | 確かめられた事実が問いに答えていない場合、答えとして見せない | 初 | 済 |
| KN-4 | 実際の社内のリポジトリと文書を調べられる。調べる範囲は、マスの設定と本人の閲覧権限で決まる | 初 | 未（見本の資料だけ） |
| KN-5 | AI が答えられないとき（根拠がない、問いに答えていない）は、担当者の番にする | 初 | 済（答えの完了と同時に、担当者の番になる。本人には、引き継いだことと理由を伝える） |
| KN-6 | 個別の1件のデータ（ログ、その記録の中身）を調べられる | 後 | 未 |
| KN-9 | 調べて答えるまでが60秒を超えたら、打ち切って担当者の番にする。調査は裏で続け、材料と案を担当者に渡す。長く待たせた末に失敗を見せない | 初 | 済（時間を超えたら担当者の番にし、調査は裏で続けて結果と案を担当者に渡す。手元のモデルでは、時間を10分にしている） |
| KN-7 | 「使い方を知りたい」には、資料に根拠がある範囲で、手順をできるだけ具体的に示す（画面の名前、押す場所、入力する値、結果の確かめ方を、操作の順に） | 初 | 一部（説明に加えて、手順を番号つきで示す（何をするか、確かめ方）。手順を出すのはモックの説明だけで、手元のモデルの説明は文章だけを返す） |
| KN-8 | 「やってほしい」でも、本人が自分でできる手順が資料にあれば、AI がその手順を示す。本人は、自分で行うか、担当者に頼むかを選べる | 初 | 済（調べて、自分でできる手順が見つかれば示す。本人は「自分でできました」か「担当者に頼む」を選ぶ。手順を出すのはモックの説明だけ） |

### 4.4 対応: 決まる、行われる

| 番号 | 要件 | 版 | いま |
| --- | --- | --- | --- |
| OP-1 | 担当者は、問い合わせをボードで見られる。列は「誰の番か」に基づく（自分の番、本人の番、相談中）。自分の番の件が一目で分かる | 初 | 一部（列は、担当者の番、相談中、本人の番、終わり。担当者の区別がないため、「自分の番」は担当者全体の番） |
| OP-2 | AI から担当者に渡る件には、材料と、判断の案が添えられる。判断の案には、相談が要るかどうかを含む。材料は、出どころごとに欄を分けて持つ（本人が選んだこと・書いたこと、照合できた資料の記述、照合できなかった内容、先例、AI の案）。どの欄に入るかは、AI ではなくコードが決める | 初 | 済（材料は、出どころごとに欄を分けている: 本人が選んだこと・書いたこと、確かめられた事実、確かめられなかった内容、同じ置き場所の先例、AI の案。案を作る実装は見本だけ） |
| OP-17 | AI の判断の案と手順の案には、基づく事実と先例を添える。基づくものがない案は出さない。担当者の画面では、AI の案を事実と区別して示す | 初 | 済（案に、基づく事実と先例を添える。どちらもない案は、コードで捨てる。画面では、案を事実と区別して示す） |
| OP-3 | AI が、本人への返信の下書きを出す。担当者が確かめ、直してから送る。AI が直接送ることはない | 初 | 済（担当者が頼むと、本人の言語で下書きを作り、入力欄に入れる。送るのは担当者。実装はモックだけ） |
| OP-4 | 担当者は、本人に聞き返せる。聞き返している間は本人の番になる | 初 | 済 |
| OP-5 | 担当者は、判断や作業の結果を本人に伝えられる。伝えると本人の番（結果を確かめる）になる | 初 | 済 |
| OP-6 | 担当者は、仕様の持ち主に相談できる。相談は、マスの設定にある相談先に届く。担当者は、相談するときに相手を替えられる。相談先が複数の人の場合は、その中の誰かが答えれば足りる。相談している間は持ち主の番になる。相談には、AI が揃えた材料が付く | 初 | 一部（相談でき、相手を替えられる。相談している間は持ち主の番。持ち主は、担当者と同じ材料を読める。相談が届くのは画面の中だけで、外への通知がない。持ち主の区別がない） |
| OP-7 | 仕様の持ち主の決定は、先例として記録される（どのマスの、どんな状況か。決定の内容。理由。決めた人。元の問い合わせ。日付）。記録するのは、相談された人が基本。会議や別の連絡手段で決まった場合は、担当者が、決めた人の名前を添えて記録できる。その場合は、決めた人に知らせ、直せるようにする | 初 | 一部（決定は、置き場所ごとの先例として残る。担当者が代わりに記録でき、持ち主が確かめるか直せる。決めた人への知らせは、持ち主の画面に出すだけ） |
| OP-8 | AI が、同じマスの似た先例を探し、担当者への材料に含める | 初 | 一部（同じ置き場所の先例を、コードが引いて材料に含め、助言が案の根拠にする。似ているかどうかの判断は、見本の実装では行っていない） |
| OP-9 | 担当者は、マスを置き直せる。種類が変われば区間も変わる。置き直しの履歴が残る | 初 | 済 |
| OP-10 | 担当者は、マスの設定に従って自動で割り当てられ、替えられる。マスの担当は、当番表（期間ごとの担当者）として設定できる | 次 | 未（担当者の区別がない） |
| OP-11 | 新しい件と本人の追記が、開いている担当者の画面に即時に届く。Slack にも投稿できる | 初 | 済 |
| OP-12 | AI が、担当者に作業の手順の案を出す。手順はできるだけ具体的にする（対象、操作やコマンド、順序、結果の確かめ方、元に戻す方法）。根拠にした資料と先例を添える。実行するのは担当者 | 初 | 済（手順の案に、対象、操作、確かめ方、元に戻す方法と、基づく事実と先例を添える。実行するのは担当者。案を作る実装は見本だけ） |
| OP-13 | 先例を、後の決定で上書きできる。上書きされた先例は、AI が案の根拠に使わない | 次 | 未 |
| OP-14 | 問い合わせを、開発の課題（外部の課題管理の URL）と結びつけられる | 次 | 未 |
| OP-16 | 担当者が貼り付けたやり取り（別の連絡手段での相談の記録など）から、AI が先例の下書き（状況、決定、理由）を作る | 次 | 未 |
| OP-15 | 本人または担当者が、その件に人を加えられる。加えられた人は、その件を見ることと追記ができ、知らせを受け取る。加える時点で、その人がその件の内容（AI が調べた資料を含む）を見てよいかを確かめる | 次 | 未 |

### 4.5 終了

| 番号 | 要件 | 版 | いま |
| --- | --- | --- | --- |
| CL-1 | 答えたのが AI でも担当者でも、本人が結果を確かめる。確かめる言葉は、答えが分かったかではなく、目的が進むかを尋ねる（「やりたかったことは、進められそうですか」）。本人が解決を伝えると「解決済み」で終わる | 初 | 済 |
| CL-2 | 本人が「解決していない」と伝えると、担当者の番になる | 初 | 済 |
| CL-3 | 担当者が応じないと決めた場合、理由を添えて伝えると「見送り」で終わる。理由は種類（再現しない、既知の制限、対象外、重複）と文章で持つ | 初 | 済（理由の種類に「その他」を足した） |

### 4.9 言語

社内には、日本語以外で問い合わせる人がいる。入口が押して答える形なので、選択肢を読めなければ最初の質問で止まる。言葉の違いは、伝える費用そのものでもある。

| LG-1 | 画面の文言を、複数の言語で表示できる。最初の版は日本語と英語。最初の表示はブラウザの言語に合わせ、本人が切り替えられる | 初 | 済 |
| LG-2 | 設定（種類、システム、機能、マスごとの質問と選択肢）に、言語ごとの名前を持てる。その言語の名前がなければ、既定の言語で表示する | 初 | 済 |

| LG-4 | 本人と担当者の言語が違う場合、担当者には訳を添えて見せる。本人が書いた原文は必ず残す。AI が出す返信の下書きは、本人の言語で書く | 初 | 済（担当者が頼むと、本人の言語で書かれた文章の下に訳を添える。原文は残す。下書きは本人の言語で書く。訳の実装はモックだけで、実際には訳さない） |

### 4.10 変更の記録

「おかしいかもしれない」の多くは、直前の変更がきっかけで起きる。変更を記録として持つと、AI が「先週の変更でこう変わった」と説明でき、同じ問い合わせが重なる前に知らせられる。

| 番号 | 要件 | 版 | いま |
| --- | --- | --- | --- |
| CH-1 | 変更（いつ、どのシステムのどの機能で、何が変わったか）を記録できる。予定の変更と、行われた変更を区別する | 次 | 未 |
| CH-2 | AI が調査で、問い合わせの時期とマスに近い変更を材料に含める。本人向けの説明にも、担当者向けの材料にも使う | 次 | 未 |
| CH-3 | 変更を、入口のお知らせ（IN-6）に出せる | 次 | 未 |
| CH-4 | 「直す」「採用する」と決まった問い合わせについて、対応する変更が行われたら本人に知らせる | 次 | 未 |
| CH-5 | 変更を、開発の課題やリリースの記録から取り込める | 後 | 未 |

## 6. Jira Service Management との突き合わせ

公式のドキュメントで確かめた（2026-11-22）。事実の記録は `jsm-benchmark.md` にある。ここには判断だけを書く。

### 6.1 JSM と同じ型のもの

型を揃える方針どおり、次は JSM の作りと一致している。新しく考える必要はなく、JSM の既定の動きを参考にできる。

| この要件定義 | JSM | 補足 |
| --- | --- | --- |
| 種類の行 | リクエストタイプ、作業タイプ | JSM は、本人に見せる窓口（リクエストタイプ）と、進み方の土台（作業タイプ）を分けている。種類ごとに通る区間を設定する CF-2 は、この分け方と同じ |
| 状態を「誰の番か」で持つ | ステータスの「サポート待ち」「顧客待ち」 | コメントした人によって番が移る既定のルールがある |
| 終わり方を、状態と別に持つ | 解決状況（Resolution）は、ステータスとは別の項目 | |
| 見送り | 解決状況の「Won't do」 | |
| 取り下げ | ステータスの「Canceled」 | |
| 仕様の持ち主への相談 | 「Escalated」のステータスと、相談用のキュー | 専用の機能はなく、ステータスとキューの組み合わせで表すのが公式の勧め方。承認の機能は可否の決裁用で、相談とは別 |
| 期限を、対応する側の番の時間で数える | SLA の一時停止の条件 | 測る2つ（最初の反応まで、結果を伝えるまで）も、JSM の既定の2つと同じ |
| 緊急度 | 優先度（緊急度と影響度から決める） | JSM は5段階で、2つの項目から決める。こちらは3段階で、項目は1つ。単純なままにする |
| 終わった件を、本人の追記で開き直す | 既定の自動化ルール | 期間の制限は、JSM でも自前で足す |
| 返事がないとき、知らせる | 顧客待ちが続くとリマインドする雛形 | 雛形の日数は5日 |
| マスごとの担当 | キュー、割り当てのルール | |
| FAQ の下書き（AC-4） | 繰り返す問い合わせから、足りない記事を提案する機能 | |

### 6.2 JSM にあって、この要件定義になかった機能

| JSM の機能 | 判断 | 理由と、反映先 |
| --- | --- | --- |
| 似た問い合わせの提示（重複の検出） | **採る**（次の版） | 繰り返す費用に効く。進行中の似た件を担当者に示し、結びつけられるようにする。AC-6 として追加 |
| ほかの課題へのリンク | **採る**（次の版） | 「直す」「採用する」と決まった件を、開発の課題と結びつける。採用後の開発は範囲外だが、行き先を示す線は要る。OP-14 として追加 |
| 入口のお知らせ | **採る**（次の版） | 既に分かっている障害や変更を入口に出し、同じ問い合わせが重なるのを防ぐ。IN-6 として追加 |
| 営業時間のカレンダー | **採る**（次の版） | 期限を営業時間で数える。MS-2 に追記 |
| 開き直したときの期限の扱い | **採る**（次の版） | JSM に合わせ、「結果を伝えるまで」は数え直し、「最初の反応まで」は数え直さない。MS-2 に追記 |
| 解決状況の細かい値（再現しない、既知の問題、重複） | **形を変えて採る**（最初の版） | 終わり方は4つのまま増やさない。見送りの理由の種類として持つ。CL-3 に追記 |
| 期限が近い順の並び | **採る**（次の版） | ボードの列の中の並びに使う。MS-2 に追記 |
| リクエストの参加者（経過を見られる人） | **採る**（次の版） | JSM と同じく、その件に人を加える形にする（OP-15）。部署などの単位で自動的に見せる形は採らない。見られたくない件が混ざるおそれがあるため |
| 承認（依頼者側の上長などの可否の決裁） | **採らない** | 承認の要る依頼は、ほとんどない。必要な場合は、担当者が本人に聞き返して了承を確かめる（OP-4）。承認者という役割と、承認待ちの状態は持たない |
| 満足度の調査 | **形を変えて採る**（次の版） | 本人が結果を確かめる流れを、終わり方に組み込んである。調査を別に送ると、同じことを2度尋ねることになる。代わりに、解決を伝えるときに任意の一言を書けるようにする（CL-10）。点数は取らない。見出しの指標は別に決めてあり、点数は答えた人の偏りを映すため |
| 定型の返信 | **採らない** | AI の返信の下書き（OP-3）が代わりになる |
| 条件つきのフォーム | **形を変えて採る**（最初の版） | 1枚のフォームにはせず、1問ずつ押して答える形にする（IN-1）。マスごとの「毎回聞くこと」（RC-2）が、フォームの項目に当たる。前の答えによって次の質問が変わる点は、条件つきのフォームと同じ |
| AI が解決の手順を実行する機能 | **手順の提示まで採る**（最初の版） | 本人と担当者に、できるだけ具体的な手順を示す（KN-7、KN-8、OP-12）。AI 自身は実行しない。JSM のこの機能にも、人が計画を確かめてから実行する動かし方がある |
| 本人の文面からの感情の分析 | **採らない** | 4つの費用に直接は効かない |
| 資産の管理、サービスの一覧 | **形を変えて採る**（最初の版） | システムと機能の台帳として持つ。置き場所の軸そのもの（CF-1、CF-3） |
| 変更の管理 | **形を変えて採る**（次の版） | 変更の記録として持つ（4.10）。可否を審議する会議やリスクの評価は作らない |
| 当番の管理 | **形を変えて採る**（次の版） | マスの担当を当番表として持つ（OP-10）。夜間や休日の呼び出しは作らない |
| インシデント、問題の管理。アラート。要員の管理 | **採らない** | 3章の「作らないもの」のとおり |
| 多言語の対応 | **採る**（最初の版） | 社内に、日本語以外で問い合わせる人がいる。画面の文言と設定を複数の言語で持ち、AI は本人の言語でやり取りする（4.9）。後から足すと設定の持ち方から直すことになるため、最初の版で作りを入れる |

### 6.3 この要件定義にあって、JSM にない機能

独自の部分。内製する意味は、ここにある。

| 独自の部分 | JSM との違い |
| --- | --- |
| 社内のソースコードを根拠にした答えと、引用の照合 | JSM の AI は、結びつけたナレッジベース（文書）を検索して要約し、参照した記事を示す。コードを読むことと、引用が実在するかを機械的に確かめることは、確認できなかった |
| 確かめられなかった内容を、本人に見せない | 同上 |
| 押して答えた内容から AI が問いを組み立て、言い直して本人に確かめる。文章で書いた場合は AI が置く | 種類を本人が選ぶ点は、JSM のリクエストタイプの選択と同じ。違いは、項目を埋めて送るのではなく、AI が問いの文章を組み立てて本人に確かめる手順があること。この手順は、JSM では確認できなかった |
| 「解決済み」と「回答済み」の区別 | JSM には、返事がないまま終わったことを表す標準の値がない。担当者が解決としたら解決になり、本人が確かめたかは満足度の調査で補う作り |
| 置き場所の格子（システム × 機能 × 種類）と、マスごとの設定 | システムと機能の2軸をそのまま持つ標準の項目は、確認できなかった。項目を足して表す形になる |
| 先例（決定の記録）と、それを AI が担当者に示すこと | 直接に当たる機能は確認できなかった。ナレッジベースの記事として書く形になる |
| 区間（分かる、決まる、行われる）と、段 | 当たる概念は確認できなかった |
| AI は閉じない、作業しない | JSM には、AI が計画から実行まで自動で進める動かし方がある |

独自の部分のうち、上の2行は内製の理由の2つ目（機密を外に出さずに AI に読ませる）に、格子とマスごとの設定は3つ目（要望にすぐ応える）に対応する。残りは、定義（不足を埋めてもらおうとする働きかけ）から導いたもので、型を揃えた結果ではない。

## 9. レビューでの決定の記録

2026-11-22 のレビューで決めたこと。理由は各章にある。

| 点 | 決定 |
| --- | --- |
| 入口の形 | 選択肢を押していく一問一答を基本にする。聞く順は、種類、システム、機能、マスごとの詳しい質問。文章で書く道を残す |
| 答えを待たずに送れる条件 | 問いを確かめた後に限る。入力は省けない。AI の調査は裏で必ず行う |
| AI と作業 | AI は作業を実行しない。手順はできるだけ具体的に示す。頼まれた作業でも、本人が自分でできる手順があれば示す |
| 資産、変更、当番 | システムと機能の台帳、変更の記録、当番表として含める |
| 最初の版の範囲 | 段階の1〜3と、期間で回答済みにする処理 |
| JSM にあった機能 | 似た問い合わせの提示、課題へのリンク、入口のお知らせ、営業時間、期限順の並びを採る（次の版）。定型の返信、感情の分析、インシデントや問題の管理は採らない |
| 言語 | 日本語と英語。画面の文言と設定を複数の言語で持ち、AI は本人の言語でやり取りする。担当者には訳を添える |
| 依頼者側の承認 | 持たない。必要なら担当者が本人に聞き返す |
| 見るだけの人 | その件に人を加える形を、次の版に置く |
| 満足度の調査 | 送らない。解決を伝えるときに任意の一言を書ける（次の版）。点数は取らない |
| 仕様の持ち主の決め方 | マスの設定の相談先を既定にし、担当者が替えられる。相談先は複数の人でもよい。先例は担当者が代わりに記録でき、決めた人に知らせる |
| 権限 | 本人と担当者で、見られる資料に基本的な差はない前提で作る。権限を受け取る境界だけ残す |
| 記録の形 | 出どころごとに5つの欄を分ける。AI の案には、基づく事実と先例を添える |
| 目的のずれ | 質問は増やさない。言い直しに目的を含め、結果を確かめる言葉を目的の側に寄せる |
| 期間と応答の目標 | 知らせるまで5営業日、終えるまでさらに5営業日。調べて答えるのが60秒を超えたら担当者の番にする |
