# いまの動きと、分かっている制約

仕様の正は、それぞれの文書にある（画面と API の間は `api-contract.md`、画面は `ux-principles.md`、スキルは `skill-architecture.md`）。この文書は、全体を1か所で見渡すための要約。食い違ったら、各文書を正とする。

## いまの動き

**入口**

- 選択肢を押していく一問一答（種類、システム、機能、詳しい質問、補足）。文章で書く道もある。押して答えるだけなら、問いを組み立てるまで AI を呼ばない。
- 設定に書いた詳しい質問は、本人の文章に答えが書かれていれば聞かない（聞き手が読み取る）。読み取った答えには注記が付き、本人が押して答え直せる。

**状態**

- 問い合わせの状態は、区間、誰の番か、待っていること、終わり方の4つ。番は、本人、AI、担当者、仕様の持ち主。担当者に渡しても問い合わせは終わらず、番が移るだけ。
- 終わらせるのは本人。担当者が終わらせられるのは、見送る場合だけ。AI は終わらせない。
- 終わった件は、本人が追記すると、担当者の番で開き直す（本人が自分で取り下げた件を除く）。

**調査**

- 調査は、問いを確かめた時点で API が始める。画面は、進み具合を見るだけ。
- 始めてから `inquiry.rules.answer-timeout`（既定60秒）が過ぎても AI の番のままなら、担当者に渡す。調査は打ち切らずに裏で続ける。API を起動し直したときも、AI の番の件は担当者に渡す。問い合わせが AI の番のまま残ることはない。
- AI が答えられなかった件（根拠がない、問いに答えていない）は、本人に選ばせず、担当者に渡す。なぜ渡ったかは `handoverReason` が持つ。
- 担当者に渡した後にも、調査は裏で行う（答えを待たずに送った件、業務が止まっている件、時間切れの件）。裏での調査の結果は、担当者だけに見せる。

**担当者と、仕様の持ち主**

- 担当者には、材料（本人が書いたこと、確かめられた事実、確かめられなかった内容、同じ置き場所の先例）と、AI の案（判断の案、手順の案）が出る。案は、基づく事実か先例を持つものだけ。
- 担当者は、返信の下書きと、本人の言語で書かれた文章の訳を、頼める。下書きは入力欄に入るだけで、AI が直接送ることはない。
- 新しい決定が要る件は、担当者が仕様の持ち主に相談する。持ち主が決めると、決定が先例として残り、担当者の番に戻る。本人に伝えるのは担当者。
- ボードは、誰の番かで列を分けて見る場所。操作は、カードを押して開く詳細のパネルで行う。

**時間**

- 本人の返事がないまま期間が過ぎた件は、1度知らせたうえで終わる（結果を伝えた後は「回答済み」、聞き返した後は「取り下げ」）。期間は営業日で数える。
- 手元で確かめるときは、`POST /api/dev/rules/run`（本番にはない）に時刻を渡して判定する。DB にある、本人の返事を待っている件のすべてが対象になる。

**言語**

- 日本語と英語。画面の文言と設定の名前は見る人の言語、書かれた内容と根拠の引用は書かれたときのまま。AI は、本人の言語で書く。

## 分かっている制約

**人の区別がない**

- 投稿者は固定の1人（`FixedCurrentUserProvider`）。担当者と仕様の持ち主にも区別がない（相談先は、設定に書いた名前だけ）。担当者向け、持ち主向け、先例の API に認証がない。
- 緊急度は、入口の間に本人が決める。入口の後に本人が上げることも、担当者が直すことも、できない。

**知らせが、画面の中だけ**

- 返事がないときの知らせと、相談は、画面を開かなければ届かない。担当者への通知だけ、Slack にも投稿できる（投稿先が未設定なら、投稿しない）。
- 本人のページは、新しい発言を自動では取りにいかない（開き直したときに取得する）。

**中身が見本**

- すべてのスキルが、モックで動く。このリポジトリが持つ実装は、モックだけ。実際のモデルをつなぐ実装（承認された環境のモデル）、指示文、評価の仕組み、実際のリポジトリを調べる実装は、本番に向けた土台として、このリポジトリの外で作る。ここには、差し替えの境界（スキルのインターフェース、`provider` の設定、一次情報の検索、閲覧権限）だけがある。
- 差し替えは、骨組みを書き換えずに、設定とクラスと上書きのファイルを足すだけでできる（ルートの `README.md` の「カスタマイズの手引き」）。骨組みの書き換えが要るもの（担当者と持ち主の認証、種類と経路、調査の流れ、言語を足すこと）も、同じ手引きに挙げてある。
- 調べられるのは、見本の資料（`mock-knowledge/`）に書かれていることだけ。モックの調査は、問いの内容にかかわらず、決まった結果を返す。
- 質問、言い直し、説明、手順、案、下書きの中身は、決まった文面。内容の質は、確かめていない。モックの訳は訳さず、原文に「【訳の見本】」の印を付けて返す。先例が似ているかどうかの判断も、していない。

**裏の処理が、API のプロセスの中で走る**

- 裏での調査と、案の作成は、API を止めると失われる。次の起動時に「失敗」になり、やり直す手段はない（担当者は、材料なしで進める）。
- 人の操作が、裏の処理の結果を保存する瞬間と重なると、「他の操作と競合しました」になることがある。やり直せば通る。

**そのほか**

- 営業日は月曜から金曜。祝日を扱わない。
- 入口の途中で止まった件を終える処理、期限、開き直せる期間は、ない（次の版）。
- 先例は、直すことも消すこともできない。

## 一度足して、削った機能

2026-11-22 の横断レビューで、骨組みの目的（スキルの置き場所と受け渡しを示す）に効いていないと判断して削った。同じものを足す前に、ここを読む。

| 削った機能 | 削った理由 |
| --- | --- |
| 担当者が頼む調べ直し | 失敗の救済のために足したが、本人が見ていた答えが本人のページから消える原因になった。答えの置き場が1つで、本人に見せた答えと担当者向けの結果を兼ねているため |
| 区間を手で変える操作 | 区間は種類で決まる。使うのは、次の版の計測 |
| 担当者が、会議などで決まった決定を代わりに記録する道。持ち主が、それを確かめる・直す道 | 脇道。先例ができる道は、持ち主の決定の1つで足りる |
| 訳の保存（同じ文章を2度訳さない） | 訳さない見本のための保存になっていた。実際のモデルをつなぐときに、費用を見て判断する |
| 相談先の3段の引き継ぎ（マス、システム、全体） | 全体で1つの一覧で、流れは通る |
| ボードのドラッグ | 落としても状態は変わらず、パネルが開くだけだった。動かせるように見えて、動かせない |
| 手元のモデル（Ollama）で動かす実装（本人向けの5つのスキル）と、評価の仕組み | 骨組みの目的（置き場所と受け渡しを示す）から最も外れていた。追従の手間がかかり、「日本語のとき、モデルに送る内容を変えない」という縛りが、骨組みの変更を難しくしていた。実際のモデルは、本番に向けた土台として作り直す。そこで分かったことは、`skill-architecture.md` の「実際のモデルをつなぐときに、引き継ぐこと」に残した。当時の実装は、コミット `c80b4c9` で読める |
